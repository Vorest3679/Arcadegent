# Arcadegent 后端编码风格

本文面向 Arcadegent 后端的人类贡献者和编码 Agent。规则按项目现有结构重写，优先解释“为什么这样审查”，而不是只列格式偏好。

> 上游参考：[sglang-omni coding-style](https://github.com/sgl-project/sglang-omni/blob/main/.claude/skills/code-review/coding-style.md)。本文保留其中通用且有效的工程约束，并按 Arcadegent 的 Python、FastAPI、Agent runtime 和测试体系做了取舍。

## 总原则

- 先遵循同文件、同模块和相邻测试已经建立的约定；没有约定时再使用本文。
- 默认目标是“在当前边界内用更少的代码正确解决问题”，不是引入更完整的抽象。
- 保持改动聚焦。不要顺便重命名、重排、格式化或重构无关代码。
- 保留现有外部契约：HTTP 字段、SSE 事件名、工具 manifest、YAML 配置键、数据库列名和环境变量名。
- 后端源码使用 Python 3.11+ 语法；跨边界数据使用 Pydantic，内部值对象优先 dataclass。
- 安全、隐私和会话隔离优先于代码简洁。

## 分层与模块边界

- `api/` 只负责 HTTP/SSE 适配、鉴权入口、请求 DTO 校验和响应映射。业务规则、Agent 编排和存储细节不得堆进路由。
- `agent/` 负责编排、上下文、运行时和工具。运行时内核只能依赖 `app.agent.*`、标准库和第三方包；现有 `test_runtime_package_boundary.py` 是硬边界。
- `services/` 负责应用服务、DTO 映射和跨模块编排，不直接依赖具体 UI、浏览器状态或数据库驱动。
- `domain/` 放领域规则和纯数据转换；不要把 HTTP、Supabase、MCP client 或某个前端组件塞进领域层。
- `infra/` 封装外部模型、数据库和网络服务。密钥、原始异常、外部响应 payload 不得越过该层泄漏。
- 跨层连接优先使用明确 DTO、`Protocol`、JSON Schema 和依赖注入。不要跨层直接读写另一个模块的内部可变状态。
- 新增适配器、Provider 或存储实现时，先确认现有 `Protocol` 和 container 装配能否承载；不要另造一套并行注册机制。

## 简洁与去重

- 只有当前已有至少两个真实调用点，并且抽象能明显降低调用方复杂度时，才新增 helper、wrapper 或抽象层。
- 只在单个地方使用的短逻辑优先内联。三层只调用一次的 `_step_one/_step_two/_step_three` 通常比一个自上而下的函数更难读。
- 不要重复实现标准库或已安装依赖已有的能力，例如 `functools`、`itertools`、`collections`、`pathlib`、`dataclasses`、Pydantic 已有校验。
- 在第二个具体实现出现前，不要提前建立 base class、registry、plugin system 或泛型框架。
- 文件接近 400 行是“是否需要拆分”的信号，不是硬阈值；一个只放 30 行单次 helper 的新文件同样可能是过度拆分。相关逻辑应放在一起。
- 删除死代码、不可达分支、注释掉的实现和没有 issue 的 TODO，不要保留“以后可能用”的空壳。

## 命名

- 类使用 `PascalCase`，函数和变量使用 `snake_case`，模块级常量使用 `UPPER_SNAKE_CASE`；保留语言要求的特殊方法名。
- 名字要表达完整语义和单位。读者不应打开函数体才知道 `distance_m`、`duration_s`、`timeout_seconds`、`max_file_bytes` 代表什么。
- 优先 `shop_id`、`session_id`、`run_id`、`source_id`、`request_id`、`route_polyline`、`origin_lng`，避免 `ctx`、`req`、`cfg`、`tmp`、`data`、`info`、`item`、`obj` 这类在具体语境中没有信息量的名字。
- 同一个值跨函数传递时保持同名；不要一会儿 `session`、一会儿 `sid`、一会儿 `record_key`。
- `API`、`DTO`、`LLM`、`MCP`、`SSE`、`JSONL`、`adcode`、`gcj02`、`wgs84` 等已是项目或外部契约的一部分，可以保留，但不要自创新缩写。
- 单字母只用于循环下标或明确的数学量。用 `h` 表示 hidden state、用 `c` 表示 conditioning 不属于数学符号。
- 外部契约名称不要为了“更好看”而重命名。数据库列、配置键、HTTP 字段、工具 schema 和第三方参数必须保持原名。
- 下划线前缀只表示“确实不应被类或模块外部调用”的实现细节。不要把它当作“内部”“私有”“只在本文件使用”的装饰性标记；新代码优先设计清晰的公开接口。

## 类型与函数签名

- 新增或修改的函数、方法和公开属性应有完整类型标注，包括参数和返回值。
- 使用 Python 3.11 的 `X | Y`、`list[T]`、`dict[K, V]`，不要新引入 `Optional`、`Union` 等旧写法。
- 容器必须参数化。`dict[str, object]`、`list[ArcadeShopSummaryDto]`、`tuple[Artifact, ...]` 比裸 `dict`、`list`、`tuple` 更可审查。
- 固定取值集合使用 `Literal[...]` 或 `Enum`，不要在多个分支里比较散落的裸字符串。
- 不要在 DTO、领域对象、仓储协议和运行时契约中新增 `Any`。外部 JSON、MCP 原始响应、动态工具参数等不可信边界可以使用 `Any` 或 `Mapping[str, object]`，但必须在边界内立即收窄，不能让 `Any` 继续流入领域逻辑。
- 不要为了清理旧代码而顺手重写所有既有 `Any`；只处理本次改动引入或直接依赖的部分。
- 回调优先定义带具名 `__call__` 的 `Protocol`。不要用 `*args`、`**kwargs` 或裸 `Callable` 隐藏真实签名。
- 不要使用可变默认值，例如 `def f(items=[])` 或 `def f(options={})`；使用 `None` 哨兵并在函数体内创建。
- 不要为了消除 lint/type 警告而删除参数；先判断参数是否真的需要。既有接口必须保留时，明确说明约束，不要假装它被使用。
- `cast`、`# type: ignore` 只能作为局部、可解释的逃生口，且应尽量换成 `isinstance` 收窄或更准确的 DTO。

## 数据结构

- 内部配置、状态和不可变值对象优先 `@dataclass`；需要不可变语义时使用 `frozen=True`，可变默认值使用 `field(default_factory=...)`。
- HTTP 请求/响应、外部输入、需要跨进程或序列化的边界数据优先 `pydantic.BaseModel`。不要在 Pydantic 已能完成校验时手写重复校验。
- 同一个概念不要同时维护 Pydantic 模型、dataclass 和裸 dict 三套形状。按角色选择一种，并在边界做明确映射。
- 从映射中删除条目使用 `mapping.pop(key)`；`del mapping[key]` 同时适用于名字和属性，语义不够明确。
- 不把敏感字段放入面向客户端的 DTO、事件 payload 或日志上下文字典。

## 导入与文件结构

- 导入按标准库、第三方、本地模块分组，组间空行；组内尽量按字母序。
- 默认在模块顶层导入。不要在函数里用局部导入来隐藏重型依赖或循环依赖。
- 只有确实为了可选依赖、导入时副作用或经过验证的循环边界时，才允许局部导入；这时应保留明确说明，并确保包边界测试能解释该例外。
- 项目内部导入优先从定义模块导入完整路径。不要新增无意义的 `__init__.py` 聚合层，也不要使用通配符导入。
- 模块级副作用只放在应用入口、container 装配或明确的生命周期模块。库模块导入时应无副作用。
- `if __name__ == "__main__"` 只出现在真正的入口模块，不放在库模块。
- 不要用临时修改 `sys.path` 的方式解决导入问题；修真正的包结构和依赖方向。

## 控制流

- 先校验输入和前置条件，再进入主逻辑。失败路径使用清晰的前置返回或抛出具体异常。
- guard clause 是允许且推荐的，不要求每个 `if` 都有 `else`。不要为了形式完整写 `else: pass`。
- 多个互斥条件优先整理成 `if/elif/else` 或提前返回，让主路径一眼可见。
- 避免深层嵌套和把多个布尔条件挤在一行。复杂条件应提取为有业务含义的名字。
- 不要在同一个函数里混合解析、校验、持久化和事件发布；按职责拆到已有层，而不是盲目新增 helper。

## 异常、失败与成熟度

- 捕获具体异常。禁止裸 `except:`，也禁止 `except Exception: pass`。
- 广泛捕获只在清理、释放锁或确保生命周期收尾时使用；必须重新抛出、记录稳定错误码或返回明确的失败结果。
- 用户输入错误、环境错误和内部不变量错误使用不同的异常类型和状态码。不要把所有失败都包成 500。
- 对外错误使用稳定错误码，例如 `executor_failed`、`persist_failed`、`skill_unavailable`；不得把原始异常消息、上游响应正文、凭据或本机路径直接返回给客户端。
- 内部不变量只在产品允许 `python -O` 移除断言的场景下使用 `assert`；否则使用显式检查并抛出明确异常。
- 不要用大块 `try/except` 防御几乎不会发生的推测性失败。主执行路径上现实会发生的错误才需要处理。
- 不要把执行失败伪造成成功输出，也不要添加不可能的 `None` 检查来掩盖已经破坏的契约。不可信结果应在边界校验，内部已知类型直接访问字段。
- 删除只为调试存在的防御代码。审查时对每个 `try/except` 和防御性 `if` 回答：删掉它会让什么失败？如果答案只是“以前调试想看”，就删除。

## 异步、并发与生命周期

- 异步函数中不要执行阻塞文件、数据库或网络 I/O；必要时使用 `asyncio.to_thread` 或已有适配层。
- 外部 HTTP、MCP 和模型调用必须有超时、取消处理和稳定的失败映射。
- 不要创建无人 await 的后台任务。必须创建时，要保存引用、处理异常，并在关闭或取消时等待清理。
- 锁的覆盖范围要尽可能小；不要在持锁状态执行不必要的 await、网络调用或用户回调。
- 并发状态必须明确归属。session、run、worker、tool task 和 skill execution 不能共享未同步的可变对象。
- 依赖 task-local 身份时使用现有 `ContextVar` 和绑定机制，不要通过模型可控制的参数冒充 agent 或会话身份。
- 取消是正常控制流，不是异常噪声。持久化、事件收尾和资源释放要能在取消后保持一致性。
- 时间间隔、冷却和重试使用单调时钟或可注入 clock；不要依赖墙钟做精确间隔。
- SSE 事件要保证顺序稳定、可重放，并有明确的终止状态；不要让异常路径留下永远等待的订阅者。

## 安全与隐私

- 所有外部输入都要在边界校验：HTTP body、query、路径参数、MCP 响应、模型工具参数、上传内容和 JSONL 行。
- 日志不得输出 `.env`、密钥、Supabase service role key、真实用户 payload、完整会话内容、原始工具参数或个人绝对路径。需要关联时使用受限引用或哈希。
- 后端密钥只能来自后端配置，不得写入 `VITE_*` 变量、返回给浏览器或进入前端包。
- SQL、RPC、HTTP 和 MCP 调用使用参数化或结构化请求；不要拼接未经校验的用户输入。
- 文件读取必须限制在允许根目录内，拒绝绝对路径、`..`、越界符号链接、非普通文件和超限内容。
- 外部请求要有 allowlist、超时和大小限制，避免让模型或用户输入任意决定目标地址。
- 错误信息、事件和调试日志都要按“可能被客户端或普通运维看到”的标准脱敏。

## 日志与配置

- 使用标准库 `logging`，每个模块创建 `logger = logging.getLogger(__name__)`。
- 沿用项目现有的惰性格式化：`logger.info("run.accepted session_ref=%s", log_ref(session_id))`。不要为了个人偏好改成一整行 f-string，也不要把敏感值直接拼进消息。
- 日志消息保持事件名加关键字段，例如 `event key=%s`；不要手写 `[Info]`、`[Warn]` 或 `[step N]` 前缀。
- `print` 只用于用户明确要看的 CLI 输出，运行期信息一律走 logger。
- 配置统一走 `Settings`、环境变量或现有配置文件。不要硬编码 URL、主机名、绝对路径或机器专属默认值。
- 有业务含义的魔数提取为模块常量；经验值要说明来源。只在一个模块使用的常量放在该模块，不为了共享而新建跨文件依赖。
- 默认值和策略参数只在一个层级声明，自上而下传递。不要在 config、factory 和低层模块各复制一份。

## 注释与文档

- 注释解释“为什么”，不复述代码“做了什么”。只给真正不直观的兼容性、时序、外部契约或安全理由写注释。
- 新增注释优先使用英文，与大多数后端源码一致；已有中文注释不要仅为统一语言而改写。用户可见文案和中文工程文档继续使用中文。
- 一个模块保留一个简短 module docstring。函数 docstring 说明契约、重要前置条件和非显然的副作用，不需要逐行叙述实现。
- 保留许可证、版权和必要的上游归属说明，但不要在源码里泄露内部仓库、私有实现或“closed source”等来源信息。
- 不添加 `# P1`、`# [FIX]`、`# === SECTION ===` 这类流程标记。TODO 必须关联具体 issue 或明确负责人。
- `# noqa: <code>` 必须给出原因；裸 `# noqa` 不接受。

## 测试

- 每个测试用例都应回答：未来哪种回归会让它变红？如果答案只是“改了测试自己”，删掉它。
- 优先覆盖真实行为：输入到输出、状态转换、错误契约、排序、幂等、取消、边界值和序列化 round-trip。
- 不要测试实现细节，例如 helper 返回的中间 tuple、内部缓存布局或可以无损重构的表示。公共契约稳定比内部结构复制更重要。
- 一个强用例优于多个重复弱用例。重复场景使用 `pytest.mark.parametrize`；只有当某一行守护独有失败时才保留。
- 外部模型、高德、Supabase、MCP 等慢边界可以 mock，但断言必须检查结果、状态变化、事件或错误，而不只是调用次数。
- 并发测试使用 event、barrier 或明确的调度点制造确定性交错，不要用固定 `sleep` 赌时序。
- 不要为了让测试通过而删断言、替换被测代码或放宽容差。契约改变时重写测试；容差扩大必须有测量依据。
- 回归测试应放在现有测试套件附近，不要为一个 case 随意新建文件。共享 fixture 放在对应 `conftest.py` 或已有 support 模块。
- 测试文件不要导入另一个测试文件；优先通过 fixture 或 support 模块共享。
- 测试不得依赖真实密钥、真实生产数据或外部网络。私有数据用例使用 `private_data` 标记并保持可跳过。
- 失败路径和受支持的 fallback 要测；不要只为保留推测性恢复代码而增加测试。

## 验证命令

- 聚焦后端测试：`python -m pytest backend/app/tests/path/to/test_file.py`
- 全量后端相关测试：`python -m pytest`
- 最后检查空白和损坏补丁：`git diff --check`
- 仓库当前没有统一的 Python formatter 配置时，不要擅自引入新 formatter，也不要顺手全局格式化。

按改动范围选择验证，不要求每次全量跑完。但报告时必须区分“已执行且通过”“未执行”“因依赖或凭据不可用而替代验证”。

## 合并前检查

- 改动是否越过 `api/`、`agent/`、`services/`、`domain/`、`infra/` 的职责边界？
- 新增类型是否让契约更清楚，而不是把 `Any` 或裸 dict 扩散到领域层？
- 失败、取消和超时是否都有确定结果，且不会伪造成功？
- 会话、worker、工具和 skill 的可变状态是否隔离？
- 日志和错误是否会泄露密钥、会话内容或本机路径？
- 测试是否能在真实回归出现时变红，而不是只锁定当前实现？
- 是否包含无关重构、临时日志、调试输出或未执行却声称完成的验证？
