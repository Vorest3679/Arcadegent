# Arcadegent 后端代码审查

用这份技能审查 `backend/app/` 下的 Python 改动，或在实现后端需求时保持同一标准。完整规则见 [Arcadegent 后端编码风格](coding-style.md)。

## 先建立证据

1. 阅读仓库根目录的 `AGENTS.md` 和改动目录附近的 `AGENTS.md`。
2. 用 `git diff`、`git status` 确认改动范围；需要时用 `git log`、`git blame` 查调用链和历史约束。
3. 找到改动的入口、调用方、被调用方和测试，不要只看 diff 本身。
4. 涉及接口、SSE、工具、存储、外部模型或地图服务时，核对契约和失败路径。
5. 逐项对照 [Arcadegent 后端编码风格](coding-style.md)；纯风格问题只引用对应规则，不扩大成泛泛重构建议。

## 审查优先级

按风险和影响排序，先查会导致错误结果、数据泄露或运行不稳定的问题。

1. **正确性与安全**：输入校验、权限、密钥、日志脱敏、路径与外部请求边界、会话隔离、失败路径。
2. **契约与边界**：HTTP/SSE DTO、工具 JSON Schema、仓储协议、Provider 协议、领域服务的职责是否被越过。
3. **生命周期与并发**：取消、超时、任务清理、锁范围、worker 隔离、本轮状态重置、事件顺序和幂等性。
4. **可维护性**：命名、类型、异常、重复抽象、配置来源、死代码和无关改动。
5. **测试**：测试是否覆盖真实回归、是否只验证实现细节、是否在失败时真的会变红。
6. **格式与行文**：只作为最后一层，不把个人偏好当成阻塞问题。

## 输出方式

先给 findings，再给必要的验证摘要。不要先写一段总结。

- **[阻塞]**：会产生错误结果、泄露敏感信息、破坏契约、造成数据丢失或稳定复现的并发问题。
- **[重要]**：高概率引入回归，或明显违反项目边界，但影响范围有限。
- **[建议]**：可维护性和一致性问题；不阻塞合并。

每条 finding 包含：

- `文件:行号`
- 问题及其实际影响
- 最小可行修复方向
- 如有关联规则，注明 `coding-style.md` 的章节

没有证据时明确写“未发现阻塞问题”，不要编造风险。不要把纯格式偏好伪装成阻塞项，也不要为了显得全面而逐条复述 diff。

## 实现模式

用户要求直接修复时：

1. 优先修根因，不做无关重构。
2. 不破坏已有 DTO、工具 schema、缓存格式或会话持久化契约；必须变更时同步迁移和兼容逻辑。
3. 先补能复现问题或锁定新契约的测试，再做最小实现。
4. 组合改动同时覆盖成功、失败、取消和边界值。
5. 运行相关 pytest；跨层契约改动再运行对应集成测试。报告实际命令和结果，不声称未执行的验证。

常用命令：

```bash
python -m pytest backend/app/tests/path/to/test_file.py
python -m pytest
git diff --check
```

如果改动影响前端请求、SSE 或地图交互，提醒需要按仓库约定补 Playwright 端到端验证，不能只凭后端测试或构建通过下结论。

## 重点边界

- `api/` 只处理 HTTP/SSE 适配，不承载 Agent 编排或领域规则。
- `agent/` 运行时内核不得依赖 `app.infra`、`app.services` 或具体数据库；已有包边界测试必须保持通过。
- `services/` 负责应用编排和映射，不直接依赖具体 UI 或浏览器状态。
- `infra/` 封装模型、存储和外部服务；密钥和外部响应不得越过边界泄漏。
- 跨层通过 DTO、`Protocol`、JSON Schema 和依赖注入连接，不跨层读取内部可变状态。
- 任何会话、worker、工具和 skill 状态都必须有明确的归属，不能因并发请求相互污染。

完成后检查 `git diff`，确认没有临时日志、调试输出、凭证、真实数据或个人绝对路径。
