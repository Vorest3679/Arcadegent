# ブラウザー位置情報と逆ジオコーディング

[简体中文](../../dev-details/浏览器定位与逆地理编码.md) · [English](../../en/dev-details/浏览器定位与逆地理编码.md) · 日本語

最終更新：2026-03-20

## 背景

セッション開始時に Agent がユーザーの暗黙の現在地を利用できるよう、新しいセッションの最初のメッセージを送る前にフロントエンドがブラウザー位置を取得します。キャッシュした位置を再利用できない場合、バックエンドが高徳 REST 逆ジオコーディング API を呼び出して地域情報を補い、Agent のコンテキストに注入します。

設計目標：

- 高徳 API key はバックエンドに置き、ブラウザーに公開しません。
- ブラウザー位置取得と地域解決を分けます。フロントエンドは座標を取得し、バックエンドが逆ジオコーディングします。
- ツール結果から Agent に推測させず、座標と地域情報を instruction に直接渡します。
- 位置取得の失敗や高徳の停止時も会話を続け、地域情報だけを省略します。

## 全体の流れ

```text
ページを開く
  -> フロントエンドがバックグラウンドで位置取得を先行し、ローカルキャッシュに保存

新しいセッションの最初のメッセージ
  -> フロントエンドが最新のブラウザー座標を要求
  -> キャッシュ位置と同等ならキャッシュの地域情報を再利用
  -> それ以外は POST /api/location/reverse-geocode
  -> バックエンドが高徳 /v3/geocode/regeo を呼び出す
  -> province/city/district/township/formatted_address を返す
  -> フロントエンドが location を POST /api/chat/sessions に追加
  -> バックエンドが client_location を session memory に保存
  -> ContextBuilder が instruction に明示的に追加
```

## フロントエンドの処理

関連ファイル：

- apps/web/src/lib/clientLocation.ts
- apps/web/src/api/client.ts
- apps/web/src/App.tsx

### 0. ブラウザー位置情報の前提条件

公開ドメインでは、navigator.geolocation は HTTPS のセキュアコンテキストでのみ動作します。localhost と 127.0.0.1 は開発環境の例外です。本番ページを HTTP で開くと、通常は位置情報の許可ダイアログが表示されません。フロントエンドは位置取得失敗として扱い、セッションリクエストに location を追加しません。

デプロイ時は、サイトが HTTPS を使用し、80 番ポートから 443 番ポートに転送されること、外側の Nginx・CDN・iframe コンテナが Permissions-Policy で geolocation を禁止していないこと、ブラウザーが以前の拒否設定を保持していないことを確認してください。

### 1. ページを開いたときにキャッシュを準備する

初期化時に App.tsx が warmupClientLocationCache() を呼び、バックグラウンドで位置取得を始めます。

clientLocation.ts の主な関数：

- getCurrentBrowserCoordinates(maximumAge)：navigator.geolocation.getCurrentPosition を呼び出します。
- readLocationCache() / writeLocationCache()：localStorage から読み書きします。
- areEquivalentLocations()：haversine 距離で座標を比較します。
- warmupClientLocationCache()：ページを開いたときにキャッシュを準備します。
- resolveClientLocationForSessionStart()：新規セッションの送信前に最新座標を取得します。

現在は 30 メートル以内を「同じ位置」と見なします。ブラウザー位置の小さな揺れによる逆ジオコーディングの繰り返しを防ぎます。

### 2. セッション開始前に逆ジオコーディングの要否を判断する

resolveLocation() は次の順序で処理します。

1. キャッシュ位置を読み取る。
2. ブラウザーから現在の座標をもう一度取得する。
3. キャッシュと現在位置が同等で、キャッシュに地域情報があれば再利用する。
4. それ以外は reverseGeocodeLocation(coords) を呼び出す。
5. 新しい座標と地域情報をキャッシュに書き戻す。

### 3. フロントエンドが呼び出すバックエンド API

エンドポイント：

```text
POST /api/location/reverse-geocode
```

リクエスト：

```json
{
  "lng": 121.4737,
  "lat": 31.2304,
  "accuracy_m": 35
}
```

レスポンス：

```json
{
  "lng": 121.4737,
  "lat": 31.2304,
  "accuracy_m": 35,
  "province": "上海市",
  "city": "上海市",
  "district": "黄浦区",
  "township": "外滩街道",
  "adcode": "310101",
  "formatted_address": "上海市黄浦区外滩街道...",
  "region_text": "上海市黄浦区外滩街道...",
  "resolved": true
}
```

## バックエンドの処理

関連ファイル：

- backend/app/protocol/messages.py
- backend/app/api/http/location.py
- backend/app/services/amap_reverse_geocoder.py
- backend/app/core/container.py

### 1. DTO

messages.py に ClientLocationContext、ReverseGeocodeRequest、ReverseGeocodeResponse の3つのモデルを追加しました。ChatRequest.location は ClientLocationContext なので、フロントエンドから返された逆ジオコーディング結果を Agent ランタイムへ渡せます。

### 2. FastAPI エンドポイント

location.py は POST /api/location/reverse-geocode を公開します。リクエスト本文を検証し、container.reverse_geocoder.reverse_geocode(request) を呼び出します。

### 3. コンテナの組み立て

起動時に container.py が既存の高徳 REST 設定を使って AMapReverseGeocoder を作成します。

- AMAP_API_KEY
- AMAP_BASE_URL
- AMAP_TIMEOUT_SECONDS

そのため、ルート計画の REST fallback と逆ジオコーディングは同じ高徳設定を使います。

### 4. 高徳 REST API の呼び出し

AMapReverseGeocoder.reverse_geocode() は次のリクエストを送ります。

```text
GET {AMAP_BASE_URL}/v3/geocode/regeo
  ?key=...
  &location={lng},{lat}
  &extensions=base
  &roadlevel=0
```

現在の実装は Python 標準ライブラリの urllib.request.urlopen() を使います。

### 5. 高徳レスポンスの解析

サービスは province、city、district、township、adcode、formatted_address を取り出し、region_text を組み立ててフロントエンドへ返します。

特別な処理：

- 直轄市では高徳の city が空配列になる場合があり、その場合は province を city として使用します。
- AMAP_API_KEY が未設定、ネットワークエラー、レスポンス形式の異常がある場合は resolved=false を返します。

## Agent コンテキストへの注入

関連ファイル：

- backend/app/agent/runtime/react_runtime.py
- backend/app/agent/context/context_builder.py

### 1. session memory に保存する

ChatRequest を受け取ると、ReactRuntime は request.location を state.working_memory["client_location"] に保存します。後続ターンで位置情報を再送しなくても、session 内で利用できます。

### 2. instruction に追加する

ContextBuilder は現在の request.location を優先し、なければ working_memory["client_location"] にフォールバックします。次の2か所に注入します。

- runtime_hint.client_location
- 「Client location context:」で始まる明示的な instruction 文

これにより Agent は WGS84 の経度・緯度、ブラウザー精度半径、省・市・区・街道、整形済み住所を直接参照できます。「近く」「現在の都市」「ルートの出発地」「地域の好み」のような暗黙の情報を解釈しやすくなります。

## フォールバックとエラー処理

- HTTPS ではない公開ページ：ブラウザーに位置許可が表示されず、フロントエンドは location を追加しません。
- ブラウザーの位置情報を拒否：フロントエンドはキャッシュに戻り、キャッシュもなければ location を省略します。
- 高徳の逆ジオコーディング失敗：経緯度だけを保持し、メッセージ送信は続行します。
- バックエンドに AMAP_API_KEY がない：resolved=false となり、チャットは続行します。
