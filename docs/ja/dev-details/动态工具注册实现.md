# 動的ツール登録の実装記録

[简体中文](../../dev-details/动态工具注册实现.md) · [English](../../en/dev-details/动态工具注册实现.md) · 日本語

## 文書の目的

この文書では、組み込み動的ツールレジストリのリファクタリングで採用した開発方針を記録します。改修前の問題、互換レイヤーではなく一度の移行を選んだ理由、移行時に変更した境界、各手順の判断根拠、現在の設計で意図的に扱っていない範囲を説明します。

コードベースを一度に更新したため、後から commit を確認したり、プラグイン拡張を検討したりするときに使えるよう、実装手順も残しています。

## 判断の前提

重要な前提は、一度限りのコードベースリファクタリングであり、旧 manifest 形式との互換性を維持する必要がないことでした。

互換性を維持する場合、provider に tools.json と tools_manifest.json、schema_model と input_schema、handler と executor の両方を扱わせ、ランタイムに形式別の分岐を追加することになります。すると整理のための変更が恒久的な移行レイヤーとなり、コードと理解の負荷が増え、文書では二つの形式を説明し続け、将来のツールパッケージ導入・削除にも旧形式の制約が残ります。

一度の更新が許されていたため、旧入口を削除して新しいモデルへ直接移行し、provider、schema、executor の責務を明確にする方針を選びました。旧 tools.json の互換分岐を残さなかった理由はこれです。

## 旧設計の問題

組み込みツールには manifest がありましたが、システムは部分的にしか動的ではありませんでした。

### 1. manifest が外部化したのは索引で、ツール本体ではなかった

旧 manifest はツール名、Pydantic の schema_model、中央 handler を指定していました。つまり参照表にすぎず、schema も実装の局所性も持っていませんでした。

### 2. schema に中央 Python 登録が必要だった

ツールを追加するには app.agent.tools.schemas に Pydantic モデルを作り、中央のマッピングに登録する必要がありました。schema はツールと一緒に管理されていませんでした。

### 3. 実行処理にも中央 handler 登録が必要だった

追加時には handlers.py に execute_xxx を作り、manifest から参照する必要もありました。manifest 上は動的に見えても、実際の業務入口は一つの Python モジュールに集まり続けます。これはプラグイン式の着脱ではなく、ハードコードされた登録を handler ファイルへ移しただけです。

### 4. 一つのツール追加で複数の中央ファイルに触れた

旧構成では通常、中央 schema、中央 handler、manifest、テストを変更する必要がありました。「ツールごとの自己記述」という目標に合いませんでした。

## リファクタリングの目標

目的は JSON を小さなファイルに分けることだけではありません。組み込みツールを provider が組み立てられる局所的な単位にすることでした。

1. **schema をツールと一緒に置く。** 追加時に schemas.py へ中央登録しなくてよい。
2. **実行処理をツールと一緒に置く。** 追加時に handlers.py へ中央登録しなくてよい。
3. **provider を業務の中心ではなく組み立て役にする。** BuiltinToolProvider は manifest と定義を読み、validator を作り、executor を呼びます。個々のツール詳細を知る必要はありません。

## 変更前と変更後

### 旧構成

```text
tools.json
  -> schema_model: app.agent.tools.schemas:SomeArgs
  -> handler: app.agent.tools.builtin.handlers:execute_some_tool

app.agent.tools.schemas
  -> Pydantic モデル
  -> 中央 schema 登録

app.agent.tools.builtin.handlers
  -> execute_db_query
  -> execute_geo_resolve
  -> execute_route_plan
  -> execute_summary
  -> ...
```

動的と呼ばれていても、schema と handler は中央登録でした。

### 新しい構成

```text
backend/app/agent/tools/builtin/
  provider.py
  tools_manifest.json
  executor_utils.py
  executors/
    db_query.py
    geo_resolve.py
    route_plan.py
    summary.py
    select_next_subagent.py
  schemas/
    db_query_tool.json
    geo_resolve_tool.json
    route_plan_tool.json
    summary_tool.json
    select_next_subagent.json
```

tools_manifest.json は総索引、schemas/*.json はツール定義本体、executors/*.py は各ツールの入口、executor_utils.py は小さな共有 helper のみを担当します。

## 移行手順と判断根拠

### 1. 実際の中央結合点を特定する

最初に JSON を編集するのではなく、どこに中央依存が残っているかを確認しました。ToolRegistry はすでにほぼ provider 化されていました。残っていたのは組み込み provider が中央 schema と中央 handler を参照する部分です。そのため ToolRegistry をさらに変更するのではなく、組み込み provider の入力と実行経路を非中央化しました。

### 2. 旧 manifest との互換性をなくす

BuiltinToolProvider が旧 tools.json と新構成を同時に扱うのをやめました。provider のモデルと文書形式を一つに保ち、テストを最終形式に集中させ、将来の bundle/plugin 機能に旧構造の制約を残さないためです。

### 3. 総 manifest と個別定義を分ける

tools_manifest.json の役割は、共有 services の宣言と読み込む tool JSON の列挙に限定しました。各 schema を manifest に埋め込みません。schemas/*.json には name、kind、description、executor、input_schema、capabilities、metadata を含めます。これにより、ツールの説明と入口をローカルなファイル範囲で把握できます。

### 4. schema を自己記述型の JSON Schema にする

問題は Pydantic 自体ではなく、schema を中央 Python モジュールに定義しなければならず、ツールが局所的に自己記述できないことでした。各 schemas/*.json に input_schema を持たせ、provider が読み込んで ToolDescriptor を通じて公開します。

これをランタイムで使えるように、JSON の読み込み、default の適用、$ref の再帰解決、anyOf / oneOf の処理、jsonschema による最終検証を行う汎用 JSON Schema 層を追加しました。この処理は[backend/app/agent/tools/schemas.py](../../../backend/app/agent/tools/schemas.py)にあります。このファイルは特定の組み込み引数モデルを集める中央ではなく、provider に依存しない JSON Schema helper になりました。

### 5. 中央 handler をツールごとの executor に置き換える

実行処理を一つの handlers.py から executors/db_query.py、geo_resolve.py、route_plan.py、summary.py、select_next_subagent.py に分けました。各定義が app.agent.tools.builtin.executors.db_query:execute のように独自の import path を指定します。provider はツール名による分岐をせず、新しいツールも中央ファイルに execute_xxx を追加せずに済み、変更範囲を executor ごとに限定できます。

### 6. 共有 helper の範囲を狭く保つ

ツール間で使う純粋な小処理として、テキストの切り詰めや地域コード・名称の正規化を [executor_utils.py](../../../backend/app/agent/tools/builtin/executor_utils.py) に残しました。ただし、名前を変えた handlers.py や新しい中央業務モジュールにしてはいけません。

### 7. provider の責務境界を再定義する

[provider.py](../../../backend/app/agent/tools/builtin/provider.py) は tools_manifest.json を読み、共有 services を解決し、各 schemas/*.json を読み、ToolDescriptor と validator を作って executor を呼びます。ツールごとの Pydantic モデルや中央 handler 名を把握せず、ツール名に応じた業務分岐もしません。provider は組み立て役です。

### 8. provider に依存しない検証エラーを追加する

組み込み検証が Pydantic に依存しなくなったため、ランタイムにも provider 中立のエラー型が必要でした。app.agent.tools.base に ToolInputValidationError を追加し、ToolRegistry.execute() で捕捉して validation_error に統一しました。

### 9. 文書とテストを更新する

manifest ガイドを[docs/guidings/内建工具清单编写指南.md](../guidings/内建工具清单编写指南.md)で更新しました。issue の追跡資料は公開文書ではなくローカルアーカイブに残しています。test_builtin_tool_provider.py と test_tool_registry.py も更新しました。実装、文書、issue 追跡の範囲をそろえるための作業です。

## 重要なファイル対応

### 旧入口から新入口へ

- 旧 backend/app/agent/tools/builtin/tools.json -> 新 backend/app/agent/tools/builtin/tools_manifest.json。
- 旧 schema_model = app.agent.tools.schemas:SomeArgs -> schemas/*.json 内の JSON Schema としての input_schema。
- 旧 handler = app.agent.tools.builtin.handlers:execute_xxx -> executor = app.agent.tools.builtin.executors.xxx:execute。

### 中央ファイルから局所ファイルへ

- app/agent/tools/schemas.py は組み込み引数モデルの中央から、汎用 JSON Schema helper に変わりました。
- backend/app/agent/tools/builtin/handlers.py は削除されました。処理は executors/*.py に分かれ、共有の純粋関数は executor_utils.py に移動しました。

## ランタイムの流れ

```text
tools_manifest.json
  -> provider が services と tool paths を読む
  -> provider が schemas/*.json を読む
  -> provider が ToolDescriptor + validator + executor を構築
  -> ToolRegistry が definitions を集約
  -> モデルが tool call を要求
  -> ToolRegistry が権限と引数を検証
  -> BuiltinToolProvider が対応する executor を呼び出す
  -> executor が BuiltinToolContext から service を取得
  -> executor が構造化結果を返す
```

この経路には中央 schema レジストリも中央 handler ディスパッチャーもありません。

## 現在の構成による利点

組み込みツールを追加する最小手順は次のとおりです。

1. schemas/ に tool JSON を追加する。
2. executors/ に executor を追加する。
3. tools_manifest.json の tools に JSON のパスを追加する。
4. 必要な場合のみ共有 services を追加する。

中央 schemas.py に Pydantic モデルを追加したり、handlers.py に execute_xxx を登録したり、ToolRegistry に組み込み用のフィールドや分岐を追加したりする必要はありません。減ったのはファイル数ではなく、中央登録点です。

## 意図的に対象外としたこと

組み込みツールを局所的に自己記述できるようにしましたが、完全なプラグインパッケージ管理システムではありません。tool bundle のディレクトリ自動検出、ZIP の一括解析とロード、bundle の導入・削除コマンド、bundle 単位のバージョン制約と署名検証、ホットプラグのライフサイクル管理は追加していません。

これらは別のプラグイン管理課題であり、範囲とリスクが大きくなるためです。今回の最優先事項は組み込み provider の境界を整えることでした。

## 今後の拡張候補

自然な拡張は二つあります。

1. **ZIP から tool bundle を読み込む。** schemas/*.json、executors/*.py、tools_manifest.json を配布単位にまとめ、provider が展開、検証、組み立てを行います。
2. **tools を一括削除する。** インストール済み bundle の削除に合わせて registry の更新、ローカル導入状態、health status を更新します。

いずれも今回の残作業ではなく、新しいプラグイン管理機能として扱うべきです。

## 結論

次の三点がそろったことが、このリファクタリングの完了条件です。

1. schema が中央 Python 登録に依存しない。
2. 実行処理が中央 handler 登録に依存しない。
3. provider がツール固有の業務判断をせず、組み立てに専念する。

これはファイル分割だけではなく、責務の再設計です。組み込みツールは、manifest をまとった静的な仕組みから、差し替え可能な provider に近づきました。
