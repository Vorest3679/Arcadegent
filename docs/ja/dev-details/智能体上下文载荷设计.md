# Agent コンテキストペイロード設計

[简体中文](../../dev-details/智能体上下文载荷设计.md) · [English](../../en/dev-details/智能体上下文载荷设计.md) · 日本語

## 文書の目的

この文書では、Arcadegent の Agent オーケストレーション、ツール設計、コンテキスト整理に関する長期的な技術制約を記録します。一度限りのパッチではなく、今後の反復で守る設計原則を説明します。

## 設計原則

### 1. Unix 哲学に従う

モジュールを分割し、それぞれが固有の役割だけを担うようにします。

- tool は実行、検索、計算、整形などの決定的な処理を担います。
- agent はコンテキスト、skill、ツールの observation をもとに推論し、回答を生成します。
- ContextBuilder はモデルが利用できるようにコンテキストを整理し、テンプレート回答を代わりに作りません。
- skill は構造化された結果の読み方をモデルに伝え、アプリケーションコードに回答テンプレートを固定しません。

したがって、次のことを避けます。

- tool の内部から LLM を呼び出す「AI の中の AI」構成。
- execution、reasoning、presentation のすべてを一つのモジュールに担わせること。
- データが大きい、または意味上複雑になったとき、単一 payload にフィールドを追加し続けること。ディレクトリ情報と詳細ブロックに分けます。

### 2. テンプレート型ではなく、LLM が支える agent を作る

agent をテンプレート結合器に退化させず、LLM を agent のために活用します。

- 最終回答は構造化コンテキストをもとに agent が生成します。summary_tool のようなテンプレート要約器を主回答経路の代替にしません。
- テンプレートは決定的な整形に限って使い、主要な推論経路にはしません。
- prompt と skill はデータの読み方や回答の構成をモデルに示し、すべての回答形式を事前に固定しません。
- モデルが重要点を見落とす場合は、テンプレート分岐を増やすのではなくコンテキスト構造を改善します。

## 現在の実装

### 1. 要約処理を tool から agent に戻す

- summary_tool は互換性のため、決定的な formatter として残しています。
- 主な回答経路は summary_agent が担当します。
- search_agent と navigation_agent は最終回答を作るために summary_tool に依存しません。

これにより、tool を tool として保ち、隠れた二つ目の LLM 呼び出しを避け、固定テンプレートではなく agent、skill、コンテキストの組み合わせで回答品質を決めます。

### 2. 「ディレクトリ情報 + 詳細」構造を使う

context_payload は、全フィールドを一つの memory_snapshot に平坦化せず階層化します。主なブロックは次のとおりです。

- directory
- query
- search_catalog
- shop_details
- route

directory は利用可能なブロック、最初に読む内容、現在の回答の焦点をモデルに伝えます。search_catalog は total、top_shops、detail_sections などの軽量な一覧情報を持ちます。shop_details は transport、arcades、comment など特定店舗の詳しい情報を持ちます。route は検索結果と混ぜず、ナビゲーションの主軸を表します。

この構成では、モデルが先に要点を把握してから詳細を読むか判断できます。大きな店舗情報が要約情報と注意を奪い合うことも減り、skill は混在した JSON の補修ではなく安定した読み取り順を説明できます。

### 3. skill は説明書であり、テンプレート集ではない

skills/*/SKILL.md は、まず directory を読むこと、search_catalog と route を主要な回答の根拠として使うこと、shop_details を補足情報として扱うこと、補足情報と主要な回答の根拠を区別することをモデルに伝えます。

固定文を出力させることではなく、構造化コンテキストを安定して読めるようにすることが skill の目的です。

directory.skills には、現在の agent が利用できる skill の名前と説明だけが含まれます。モデルは read_skill で本文と参照資料を必要に応じて読み込み、読み込んだ内容は現在のターンのコンテキストに保持されます。ツール履歴には読み取り receipt だけを保存します。設定、更新、分離の規則は[スキル設定と拡張ガイド](../guidings/技能配置与扩展指南.md)を参照してください。

## 今後の開発制約

tool、subagent、コンテキストブロックを追加するときは、次を確認します。

1. このモジュールは一種類の役割だけを担っているか。
2. この機能は tool、agent、context builder、skill のどこに属するか。
3. 新しいフィールドは一覧情報か詳細情報か。
4. 大きなフィールドを catalog ではなく詳細ブロックに分けるべきか。
5. agent をテンプレート型に退化させていないか。
6. tool 内にネストした LLM 呼び出しを導入していないか。

## まとめ

Arcadegent の設計方針は、明確な責務境界で agent を構成し、構造化コンテキストで LLM を支え、skill で読み取り方を示し、tool で決定的な実行を保つことです。これを、コンテキスト、要約、subagent を今後発展させる際の既定の技術方針とします。
