# 評価システムの起動と設定ガイド

[简体中文](../../guidings/评测系统启动与配置指南.md) · [English](../../en/guidings/评测系统启动与配置指南.md) · 日本語

このガイドでは、Arcadegent の評価ワークベンチ（`evaluate/`）の設定と起動方法を説明します。ゼロから smoke 評価を 1 回通す手順、複数モデルの並行比較、LLM judge と人手レビューの有効化、そしてすべての設定項目の意味とデフォルト値です。評価の仕組みと指標の定義は [評価ワークベンチのアーキテクチャと実装](../dev-details/评测工作台架构与实现.md) を参照してください。

## 1. 評価の種類

| モード | コマンド | 実モデルを呼ぶか | 用途 |
| --- | --- | --- | --- |
| オフライン契約回帰 | `python -m evaluate check` | 呼ばない。ネットワーク禁止 | PR / CI でプロトコルと業務契約の退行を検査 |
| オンラインモデル評価 | `python -m evaluate validate / compatibility / run` | 呼ぶ。API 費用が発生 | 凍結ケースでモデルを比較 |
| 品質採点とレビュー | `python -m evaluate grade / review / compare` | `grade` は judge モデルを呼ぶ。他は呼ばない | 保存済み実行の再採点、人手レビュー、比較 |

オフライン回帰には設定が不要です。オンライン評価の設定はすべて `evaluate/.env` にまとまっています。

## 2. 環境の準備

Python 3.11+ が必要です。すべてのコマンドは **リポジトリのルート** で実行します。

```bash
python -m pip install -e './backend[dev]'
```

評価専用の仮想環境を作ることを勧めます。例：

```bash
python3.11 -m venv evaluate/.venv
evaluate/.venv/bin/python -m pip install -e './backend[dev]'
# 以降の python を evaluate/.venv/bin/python に置き換えるか、先に source evaluate/.venv/bin/activate する
```

`evaluate/.venv/` は Git で無視されています。

## 3. オフライン契約回帰

```bash
python -m evaluate check --suite contracts                      # evaluate/checks のみ
python -m evaluate check --suite backend                        # backend/app/tests も含める（デフォルト）
python -m evaluate check --suite contracts -k native_tool_round_trip   # 名前で絞り込み
python -m evaluate check --suite contracts --output evaluate/reports/my-check
```

| 引数 | デフォルト | 説明 |
| --- | --- | --- |
| `--suite` | `backend` | `contracts` または `backend` |
| `-k` | 空 | pytest に渡す絞り込み式 |
| `--output` | `evaluate/reports/<タイムスタンプ-乱数>/` | レポートディレクトリ。相対パスはリポジトリルート基準。既に存在すると実行を拒否 |

テスト中はすべてのソケット接続が拒否されます。`ARCADEGENT_PUBLIC_CI=1` を設定すると、ローカルの非公開データが必要なテストをスキップします（公開 CI はこの設定で動いています）。終了コードは pytest のもので、スキップが 1 件でもあるとレポートの `complete` は `false` になります。

## 4. オンライン評価：5 分で smoke を通す

### 4.1 設定ファイルの作成

```bash
python -m evaluate init-env
```

`evaluate/.env.example` を `evaluate/.env`（権限 `0600`）にコピーします。ファイルが既にあれば上書きしません。

### 4.2 モデルを 1 つ記入する

`evaluate/.env` を開き、少なくとも次の 4 項目を記入します。

```dotenv
EVAL_LLM_API_KEY=あなたのキー
EVAL_LLM_BASE_URL=https://サービスのアドレス/v1
EVAL_LLM_MODEL=アカウントで実際に使えるモデルID
EVAL_LLM_API_MODE=chat_completions      # Responses プロトコルなら responses
```

- `BASE_URL` に `/chat/completions` や `/responses` を付けず、キー、クエリ、認証情報も URL に入れないでください。
- プロトコルは明示する必要があり、失敗しても別のプロトコルに自動では切り替わりません。

### 4.3 確認、プローブ、実行

```bash
python -m evaluate validate        # モデルは呼ばない：マスキング済みの実行計画を表示し、設定漏れを確認
python -m evaluate compatibility   # profile ごとに最大 2 回の実リクエストで、ネイティブなツール呼び出しを確認
python -m evaluate run             # ケースを実行。デフォルトは合成 smoke ケース 3 件
```

実行が終わるとターミナルにレポートディレクトリが表示されるので、その中の `summary.md` を開いて結果を確認します。各ファイルの意味は [アーキテクチャ文書の第 9 節](../dev-details/评测工作台架构与实现.md#9-証跡とレポート) を参照してください。

## 5. 設定の効き方

### 5.1 設定元と優先順位

優先度の高い順に：

1. コマンドライン引数（`--models`、`--cases`、`--repeat`、`--env-file`、`--output`）
2. シェルに設定済みの `EVAL_*` 環境変数
3. `--env-file` で指定したファイル（デフォルトは `evaluate/.env`）
4. コード内のデフォルト値

読み込まれるのは `EVAL_` で始まる変数だけです。ルートの `.env` やその他の本番変数はすべて無視され、dotenv は `${VAR}` の展開もしません。

### 5.2 相対パス

- `EVAL_CASES`、`EVAL_DATA`、`--cases` の相対パスは `evaluate/` ディレクトリ基準
- `--output`、`--run`、`--env-file`、`--file`、`--baseline`、`--candidate` の相対パスは現在の作業ディレクトリ基準
- `check --output` はリポジトリルート基準

### 5.3 モデル profile の命名規則

`EVAL_MODELS` はカンマ区切りの profile 名のリストです（小文字で始まり、小文字・数字・アンダースコアのみ、重複不可）。各 profile の変数の接頭辞は次のとおりです。

| profile | 接頭辞 |
| --- | --- |
| `default` | `EVAL_LLM_` |
| それ以外の名前（例：`kimi`） | `EVAL_KIMI_` |
| judge | `EVAL_JUDGE_` |

profile 同士は **継承しません**。`kimi` に温度や価格を設定しても `default` には影響せず、その逆も同じです。

## 6. 設定項目リファレンス

「コードのデフォルト」は変数が未設定のときの値、「テンプレート値」は `.env.example` にあらかじめ書かれた値です。両者が異なる場合は、実際に書き込んだ値が使われます。

### 6.1 実行範囲

| 変数 | コードのデフォルト | テンプレート値 | 説明 |
| --- | --- | --- | --- |
| `EVAL_MODELS` | `default` | `default` | 評価する profile のリスト。`--models` で上書き可 |
| `EVAL_CASES` | `datasets/public/smoke.yaml` | 同左 | ケースファイル。`--cases` で上書き可 |
| `EVAL_DATA` | `fixtures/arcades/synthetic.jsonl` | 同左 | ゲームセンターデータの JSONL。ケースで使う店舗 ID を含む必要がある |
| `EVAL_REPEAT` | `1` | `1` | ケースごとの繰り返し回数。`--repeat` で上書き可 |

### 6.2 予算とタイムアウト

| 変数 | コードのデフォルト | テンプレート値 | 説明 |
| --- | --- | --- | --- |
| `EVAL_MAX_REQUESTS` | `40` | `40` | 今回の実行で全モデルが共有する Agent リクエストの上限 |
| `EVAL_MAX_CALLS_PER_ATTEMPT` | `40` | `40` | attempt あたりのモデルリクエスト上限（主 agent + worker）。ランタイムのステップ上限も兼ねる |
| `EVAL_MAX_TOOL_CALLS` | `40` | `40` | attempt あたりのツール呼び出し上限 |
| `EVAL_MAX_OUTPUT_TOKENS` | `32768` | `32768` | Agent リクエストごとの出力 token 上限。小さすぎるとツール呼び出しが切り詰められる（`finish_reason=length`） |
| `EVAL_REQUEST_TIMEOUT_S` | `45` | `45` | HTTP リクエストごとのタイムアウト。judge を含むすべての profile に適用 |
| `EVAL_ATTEMPT_TIMEOUT_S` | `300` | `300` | attempt 全体のタイムアウト。judge の 1 回の採点にも使う |
| `EVAL_REQUEST_INTERVAL_S` | `1` | `1` | 各モデルリクエスト前の待機秒数。レート制限を避けるため |
| `EVAL_MAX_MODEL_CONCURRENCY` | `0` | `0` | 同時に実行するモデル profile の数。`0` ならすべての profile を同時に実行。複数の profile が同じプロバイダーアカウントを共有する場合は、レート制限を避けるため小さくする |

**全体予算の決め方**：複数モデルでの完全実行の最悪ケースのリクエスト数は「モデル数 × ケース数 × 繰り返し数 × attempt あたり上限」です。たとえば 4 モデル、38 ケース、繰り返し 1 回、attempt あたり 40 回なら、全体予算切れで未実行になる attempt を出さないために `EVAL_MAX_REQUESTS=6080` が必要です。これは安全上限にすぎず、実際のリクエスト数は通常これよりずっと少なく、費用の上限でもありません。

### 6.3 モデル profile

次の接尾辞は、どの profile 接頭辞（`EVAL_LLM_`、`EVAL_<NAME>_`、`EVAL_JUDGE_`）にも使えます。

| 接尾辞 | デフォルト | 説明 |
| --- | --- | --- |
| `API_KEY` | 空 | 必須 |
| `BASE_URL` | 空 | 必須。HTTP(S)、パスの接尾辞・認証情報・クエリなし |
| `MODEL` | 空 | 必須。アカウントで使えるモデル ID |
| `API_MODE` | `chat_completions` | `chat_completions` または `responses` |
| `AUTH_HEADER` | `Authorization` | 認証ヘッダー名。サービスによっては `api-key` など |
| `SEND_TEMPERATURE` | `true` | サービスが temperature を受け付けない場合は `false` |
| `TEMPERATURE` | `0.2` | |
| `TOKEN_PARAMETER` | `max_tokens` | サービスによっては `max_completion_tokens` |
| `MAX_OUTPUT_TOKENS` | Agent は `EVAL_MAX_OUTPUT_TOKENS`、judge は `4096` | profile 単位の出力上限 |
| `EXTRA_PARAMETERS` | `{}` | 追加のリクエストパラメータの JSON オブジェクト（思考モードの切り替えなど）。`model`、`messages`、`input`、`tools`、`tool_choice`、`stream`、`instructions`、`headers` は含められない |
| `STREAM` | `false` | `true` にするとストリーミングでリクエストし、内部で完全なレスポンスにまとめる。ストリーミングと非ストリーミングの比較用で、判定は変わらない |
| `INPUT_PRICE` / `OUTPUT_PRICE` | 空 | 100 万 token あたりの単価。未設定なら費用は `null` |
| `CACHED_INPUT_PRICE` | `INPUT_PRICE` と同じ | キャッシュヒットした input の単価 |
| `OFFPEAK_INPUT_PRICE` / `OFFPEAK_CACHED_INPUT_PRICE` / `OFFPEAK_OUTPUT_PRICE` | 空 | 任意の閑散時間帯価格。3 つすべて設定した場合のみ有効で、レポートの閑散時費用にだけ影響 |

### 6.4 LLM judge

| 変数 | コードのデフォルト | 説明 |
| --- | --- | --- |
| `EVAL_JUDGE_ENABLED` | `false` | 有効にすると完全な `EVAL_JUDGE_*` profile が必要 |
| `EVAL_JUDGE_API_KEY` / `BASE_URL` / `MODEL` / `API_MODE` | — | 6.3 と同じ。評価対象とは別のプロバイダーでもよい |
| `EVAL_JUDGE_MAX_REQUESTS` | `20` | judge 専用のリクエスト予算。Agent の予算は使わない |
| `EVAL_QUALITY_THRESHOLD` | `75` | 0–100。judge のスコアがこれ以上なら品質合格 |

### 6.5 地図とその他

| 変数 | コードのデフォルト | テンプレート値 | 説明 |
| --- | --- | --- | --- |
| `EVAL_MAP_MODE` | `disabled` | `disabled` | `live` にするとナビゲーションケースが実際の AMap ルートサービスを呼ぶ |
| `EVAL_AMAP_API_KEY` | 空 | 空 | AMap Web サービスのキー。評価専用キーを推奨 |
| `EVAL_CURRENCY` | `unspecified` | `CNY` | レポートの通貨ラベル。すべての profile の単価は同じ通貨にする |

## 7. よくあるシナリオ

### 7.1 複数モデルの並行比較

```dotenv
EVAL_MODELS=deepseek,glm,kimi
EVAL_DEEPSEEK_API_KEY=...
EVAL_DEEPSEEK_BASE_URL=...
EVAL_DEEPSEEK_MODEL=...
EVAL_GLM_API_KEY=...
EVAL_GLM_BASE_URL=...
EVAL_GLM_MODEL=...
EVAL_KIMI_API_KEY=...
EVAL_KIMI_BASE_URL=...
EVAL_KIMI_MODEL=...
# 任意：価格
EVAL_KIMI_INPUT_PRICE=...
EVAL_KIMI_OUTPUT_PRICE=...
```

profile ごとのキューは同時に動き、同じ profile 内ではケースが順番に実行されます。複数の profile が同じプロバイダーアカウントを共有する場合は、`EVAL_MAX_MODEL_CONCURRENCY=1`（または小さな値）でレート制限を避けられます。一部だけを選んで実行することもできます。

```bash
python -m evaluate run --models deepseek,kimi --repeat 3
```

設定が欠けた profile があっても実行は中止されず、その attempt は `missing_model_configuration` として未実行になります。この場合 `validate` は終了コード 2 を返すので、実行前に直してください。

### 7.2 開発セット全体の実行

開発セットではケースとデータの両方を切り替えます。

```dotenv
EVAL_CASES=datasets/public/benchmark.yaml
EVAL_DATA=<ローカルのジオコーディング済みゲームセンター JSONL。evaluate/ 基準。パスの例は .env.example のコメントを参照>
```

38 ケースのうち、ナビゲーションの 4 ケースはオンライン地図を有効にした場合のみ実行されます。

```dotenv
EVAL_MAP_MODE=live
EVAL_AMAP_API_KEY=AMapのWebサービスキー
```

地図を有効にしないとナビゲーションケースは `live_map_not_configured` となり、累積加重完全合格スコアは最大 80（ナビゲーションが 20 点分）にとどまります。比較する実行同士では地図モードを揃えてください。

### 7.3 judge の有効化、再採点、人手レビュー

```dotenv
EVAL_JUDGE_ENABLED=true
EVAL_JUDGE_API_KEY=...
EVAL_JUDGE_BASE_URL=...
EVAL_JUDGE_MODEL=...
EVAL_JUDGE_MAX_REQUESTS=50
EVAL_QUALITY_THRESHOLD=75
```

`EVAL_JUDGE_MAX_REQUESTS` は実行予定の attempt 数以上にしてください。足りないと後半の attempt が採点されません。

```bash
# 保存済みの実行に judge だけを再実行（Agent は再実行しない）
python -m evaluate grade --run evaluate/reports/<run_id>

# 人手レビュー
python -m evaluate review export --run evaluate/reports/<run_id>
#   生成された review-template.jsonl を編集：quality_pass（true/false）、reviewer、reason を記入し、evidence_refs には有効な ID を残す
python -m evaluate review import --run evaluate/reports/<run_id> --file レビュー結果.jsonl

# 2 回の実行の比較（データ、ケース、地図モードが一致している必要あり）
python -m evaluate compare --baseline evaluate/reports/<A> --candidate evaluate/reports/<B>
```

### 7.4 別の設定ファイルを使う

```bash
python -m evaluate run --env-file evaluate/.env.nightly --output evaluate/reports/nightly-01
```

`evaluate/.env*`（`.env.example` を除く）は Git で無視されるので、シナリオごとに複数の設定を保存できます。

### 7.5 推奨する組み合わせ

| シナリオ | 推奨 |
| --- | --- |
| 新しいモデルを初めて試す | smoke ケース、`EVAL_REPEAT=1`、デフォルトの予算。先に `compatibility` を通す |
| リリース前の複数モデル比較 | 開発セット、`EVAL_REPEAT=3`、最悪ケースに合わせた全体予算、オンライン地図を有効、judge を有効 |
| judge の校正 | 小規模に実行し、`review export` で人手レビューして judge の結果と照らし合わせてから `EVAL_QUALITY_THRESHOLD` を調整 |
| 1 ケースのデバッグ | そのケースだけを含む YAML を作り、`--cases` で指定 |

## 8. コマンドと終了コード早見表

| コマンド | よく使う引数 | 終了コード |
| --- | --- | --- |
| `check` | `--suite`、`-k`、`--output` | pytest のもの |
| `init-env` | — | 0 |
| `validate` | `--env-file`、`--models`、`--cases`、`--repeat` | 0：設定が完全。2：profile か judge の設定が不足、または設定エラー |
| `compatibility` | 同上 + `--output` | 0：すべて合格。1：失敗または未実行あり |
| `run` | 同上 + `--output` | 0：すべて完全合格。1：不合格・未実行・未採点あり。2：設定エラー。130：Ctrl+C で中断（途中結果は保存） |
| `grade` | 同上 + `--run`（必須） | 0：すべて有効に採点。1：未完了の採点あり |
| `review export / import` | `--run`、`--file` | 0。検証に失敗するとエラーになり、何も書き込まない |
| `compare` | `--baseline`、`--candidate` | 0。指紋が一致しないとエラー |

## 9. よくある問題

| 症状 | 原因と対処 |
| --- | --- |
| `配置错误：EVAL_XXX_BASE_URL must be ...` | URL にパスの接尾辞、クエリ、認証情報が含まれている。純粋なサービスアドレスにする |
| `评测未能完成：ValueError` | ケースやデータの検証に失敗した（店舗 ID がデータにない、YAML の形式エラーなど）、またはレポートディレクトリが既に存在する。安全のため例外の型しか表示しないので、ケース、データのパス、`--output` を確認する |
| attempt の状態が `budget_exhausted` | attempt あたりのリクエストまたはツール呼び出しの上限に達した。`EVAL_MAX_CALLS_PER_ATTEMPT` / `EVAL_MAX_TOOL_CALLS` を引き上げる |
| `run_request_budget_exhausted` が大量に出る | 全体予算が小さすぎる。6.2 の式に従って `EVAL_MAX_REQUESTS` を引き上げる |
| 回答が切り詰められる、`finish_reason=length` | `EVAL_MAX_OUTPUT_TOKENS` またはその profile の `MAX_OUTPUT_TOKENS` を引き上げる |
| サービスが temperature や `max_tokens` を拒否する | `SEND_TEMPERATURE=false` にする、または `TOKEN_PARAMETER` を `max_completion_tokens` に変える |
| 費用が `null` / 未定価のリクエストがある | 単価が未設定、またはプロバイダーが完全な usage を返していない。これらのリクエストは無料とはみなされない |
| judge の結果が grader error | judge の出力が正しい JSON でない、スコアが範囲外、存在しない証拠を引用した。より安定した judge モデルに替えて `grade` で再採点する |

## 10. セキュリティ上の注意

- `evaluate/.env` には評価専用のキーだけを入れ、本番のキーを流用しないでください。
- レポートディレクトリにはプロンプト、ツール結果、回答が保存され、ローカルの業務データを含む可能性があります。`evaluate/reports/` は Git で無視されています。レポートをコミット・公開しないでください。
- レポート内のキー、認証ヘッダー、URL クエリのキー/トークンは自動でマスキングされますが、それでもレポートは非公開データとして扱ってください。
