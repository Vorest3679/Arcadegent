# Writing the Built-in Tool Manifest

[简体中文](../../guidings/内建工具清单编写指南.md) · English · [日本語](../../ja/guidings/内建工具清单编写指南.md)

This guide is for maintainers of the built-in dynamic tool registry. It focuses on:

- [backend/app/agent/tools/builtin/tools_manifest.json](../../../backend/app/agent/tools/builtin/tools_manifest.json)
- [backend/app/agent/tools/builtin/schemas/db_query_tool.json](../../../backend/app/agent/tools/builtin/schemas/db_query_tool.json)

The current design no longer inlines every tool into one large JSON file or relies on centralized schemas.py and handlers.py to enumerate each built-in tool. It works more like a plugin system:

1. tools_manifest.json declares shared services and the tool JSON files to load.
2. Each tool has its own JSON file containing its name, description, input schema, executor, and metadata.
3. BuiltinToolProvider assembles these files at startup.

If JSON is unfamiliar, remember these four rules:

- Strings use double quotes, never single quotes.
- Write each object field as "field": value.
- Separate entries with commas, except after the last entry.
- JSON has no comments; put explanations in documentation instead.

## 1. Overall structure

### 1.1 tools_manifest.json

The manifest has this shape:

```json
{
  "services": {
    "...": {}
  },
  "tools": [
    "schemas/db_query_tool.json",
    "schemas/route_plan_tool.json"
  ]
}
```

- services describes how shared runtime dependencies are constructed.
- tools lists the tool JSON files to load, usually with paths relative to the manifest.

In order, the loader constructs services and then reads each tool JSON to register a built-in tool.

### 1.2 One tool JSON file

A minimal example:

```json
{
  "name": "summary_tool",
  "kind": "function",
  "description": "Format a deterministic text summary from structured search or navigation context.",
  "executor": "app.agent.tools.builtin.executors.summary:execute",
  "input_schema": {
    "type": "object",
    "properties": {
      "topic": {
        "enum": ["search", "navigation"],
        "type": "string"
      }
    },
    "required": ["topic"],
    "additionalProperties": false
  }
}
```

Adding a built-in tool usually means adding its path to tools_manifest.json, creating its tool JSON, and adding an executor in the appropriate Python module if the execution logic is specialized.

## 2. Defining services

services is an object whose keys are service names and whose values are service configurations.

```json
{
  "services": {
    "amap_config": {
      "factory": "app.agent.tools.builtin.route_plan_tool:AMapConfig",
      "dependencies": {
        "api_key": {
          "env": "AMAP_API_KEY",
          "default": ""
        },
        "base_url": {
          "env": "AMAP_BASE_URL",
          "default": "https://restapi.amap.com"
        },
        "timeout_seconds": {
          "env": "AMAP_TIMEOUT_SECONDS",
          "default": 8.0,
          "cast": "float"
        }
      }
    }
  }
}
```

- factory (required): import path in module.path:object_name form.
- dependencies (optional): constructor arguments passed to the factory.
- singleton (optional): defaults to true; create and cache the service once.

### 2.1 Reference another service directly

```json
{
  "dependencies": {
    "store": "store",
    "amap_config": "amap_config"
  }
}
```

The strings store and amap_config are resolved as service names.

### 2.2 Read an environment variable

```json
{
  "dependencies": {
    "timeout_seconds": {
      "env": "AMAP_TIMEOUT_SECONDS",
      "default": 8.0,
      "cast": "float"
    }
  }
}
```

Supported fields are env (environment-variable name), default (value when the variable is absent), and cast. Supported casts are int, float, bool, and string.

### 2.3 Use an explicit reference

```json
{
  "dependencies": {
    "project_root": {
      "ref": "project_root"
    }
  }
}
```

ref is similar to a direct service-name string and also supports dotted paths:

```json
{
  "dependencies": {
    "base_url": {
      "ref": "settings.amap_base_url"
    }
  }
}
```

### 2.4 Resolve a path

```json
{
  "dependencies": {
    "prompt_path": {
      "path": "app/agent/context/skills/response-composition/SKILL.md",
      "base": "project_root",
      "as_string": true
    }
  }
}
```

- path: relative or absolute path.
- base: service used as the base for a relative path; defaults to project_root.
- as_string: return a string path when true, otherwise a Path object.

### 2.5 Set a literal value

```json
{
  "dependencies": {
    "provider": {
      "value": "amap"
    }
  }
}
```

### 2.6 Nested objects and arrays

When a value is itself an object or array, the loader recursively resolves ref, env, path, and value entries inside it.

## 3. Defining a tool JSON file

Each tool JSON file is a standalone object.

- name (required): unique registered tool name.
- kind (optional): usually function.
- description (required): explains the tool's purpose to the model.
- executor (required): Python callable in module.path:object_name form.
- input_schema (required): JSON Schema exposed to the model and used for runtime validation.
- capabilities (optional): string array of capability labels.
- metadata (optional): additional metadata; it supports resolution similar to dependencies.

### Executor format

The format must be:

```text
module.path:object_name
```

Examples include app.agent.tools.builtin.executors.route_plan:execute and app.agent.tools.builtin.executors.summary:execute. Omitting the colon causes the runtime to report invalid_import_path.

## 4. Writing input_schema

input_schema uses standard JSON Schema. The current loader applies defaults for missing fields first, then performs strict JSON Schema validation.

Recommendations:

- Give optional fields an explicit default.
- Set additionalProperties to false when extra fields are not allowed.
- Use enum to constrain values.

Example with a default:

```json
{
  "input_schema": {
    "type": "object",
    "additionalProperties": false,
    "properties": {
      "sort_order": {
        "type": "string",
        "enum": ["asc", "desc"],
        "default": "desc"
      }
    }
  }
}
```

If the model omits sort_order, the runtime fills in desc.

## 5. Complete tool example

This example is close to the repository's route_plan_tool:

```json
{
  "name": "route_plan_tool",
  "kind": "function",
  "description": "Plan a route from origin to destination.",
  "executor": "app.agent.tools.builtin.executors.route_plan:execute",
  "capabilities": ["builtin", "read_only", "navigation"],
  "metadata": {
    "guide": {
      "path": "app/agent/context/skills/navigation-result-reading/SKILL.md",
      "base": "project_root",
      "as_string": true
    }
  },
  "input_schema": {
    "$defs": {
      "LocationArgs": {
        "type": "object",
        "additionalProperties": false,
        "properties": {
          "lng": { "type": "number" },
          "lat": { "type": "number" }
        },
        "required": ["lng", "lat"]
      }
    },
    "type": "object",
    "additionalProperties": false,
    "properties": {
      "provider": { "type": "string", "enum": ["amap", "google", "none"] },
      "mode": { "type": "string", "enum": ["walking", "driving"] },
      "origin": { "$ref": "#/$defs/LocationArgs" },
      "destination": { "$ref": "#/$defs/LocationArgs" }
    },
    "required": ["provider", "mode", "origin", "destination"]
  }
}
```

## 6. Minimal steps to add a built-in tool

1. Add a file path to the tools array in [backend/app/agent/tools/builtin/tools_manifest.json](../../../backend/app/agent/tools/builtin/tools_manifest.json).
2. Create a tool JSON under [backend/app/agent/tools/builtin/schemas](../../../backend/app/agent/tools/builtin/schemas) with name, description, executor, and input_schema.
3. If the tool needs a new shared dependency, add its factory and dependencies to services in the manifest.
4. If the execution logic is specialized, add an executor module under [backend/app/agent/tools/builtin/executors](../../../backend/app/agent/tools/builtin/executors).

## 7. Design trade-offs

The structure means adding a built-in tool no longer requires edits to centralized schemas.py or handlers.py. The tool schema is the JSON file itself, closer to a self-describing provider/plugin definition, and the tool's description, arguments, and execution entry point stay together.

Specialized execution logic still requires a Python executor. However, that code belongs to the tool's own module instead of requiring registration in a centralized handlers file. This is the main benefit of the split.
