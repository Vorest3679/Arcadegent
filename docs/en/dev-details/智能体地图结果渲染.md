# Rendering Agent Map Results

[简体中文](../../dev-details/智能体地图结果渲染.md) · English · [日本語](../../ja/dev-details/智能体地图结果渲染.md)

Last updated: 2026-04-15

## Goal

This document explains how the backend exposes map-related artifacts to the frontend and how the frontend loads them into map components.

The implementation keeps a clear boundary:

- The assistant body remains Markdown.
- The map does not come from free-form HTML or TSX generated by the model.
- Structured backend artifacts drive the map, rendered by fixed React components.

```text
assistant markdown text
  + structured map artifacts
  -> ChatPanel
  -> AgentMapCard
  -> AmapMapCanvas / AmapShopMarkers / AmapRouteOverlay / MapActionBar
```

## Data entry points

The frontend receives map artifacts through two paths.

### 1. Restore from session details

When a historical session is loaded or its details are refreshed, the frontend calls GET /api/chat/sessions/{session_id}. The backend's ChatSessionDetail includes map fields such as:

```json
{
  "shops": [],
  "route": null,
  "client_location": null,
  "destination": null,
  "view_payload": null
}
```

In App.tsx, mapArtifactsFromSession(detail) converts these fields to a unified ChatMapArtifacts:

```ts
type ChatMapArtifacts = {
  shops: ArcadeSummary[];
  route?: RouteSummary | null;
  client_location?: ClientLocationContext | null;
  destination?: ArcadeSummary | null;
  view_payload?: Record<string, unknown> | null;
  route_pending?: boolean;
};
```

Artifacts are written to activeMapArtifacts only when route, destination, shops, or view_payload is present.

### 2. Progressive route events over SSE

During navigation, the backend sends navigation.route_ready. Its data is handled as a RouteSummary, for example:

```json
{
  "provider": "amap",
  "mode": "walking",
  "distance_m": 1280,
  "duration_s": 960,
  "origin": {
    "lng": 121.4,
    "lat": 31.2,
    "coord_system": "wgs84",
    "source": "client",
    "precision": "approx"
  },
  "destination": {
    "lng": 121.475,
    "lat": 31.228,
    "coord_system": "gcj02",
    "source": "route",
    "precision": "approx"
  },
  "polyline": [],
  "hint": null
}
```

App.tsx performs lightweight validation with coerceStreamRoute(envelope.data) and, on success, updates activeMapArtifacts with the route and route_pending: true. It retains previous shops, client_location, and destination, and supplies a default view_payload when necessary. This lets the route card appear before the final assistant text.

After assistant.completed, the frontend fetches the session details again. The complete artifacts from the session replace the pending state and route_pending becomes false.

## Backend artifact contract

### shops

Used for candidate arcade map cards. Each arcade should include at least source_id, name, address, city_name, and geo.gcj02 coordinates. For example:

```json
{
  "source_id": 101,
  "name": "Arcade One",
  "address": "Nanjing East Road",
  "city_name": "上海市",
  "geo": {
    "gcj02": {
      "lng": 121.475,
      "lat": 31.228,
      "coord_system": "gcj02",
      "source": "geocode",
      "precision": "approx"
    },
    "source": "geocode",
    "precision": "approx"
  }
}
```

The frontend uses only geo.gcj02 for map markers. An arcade without geo.gcj02 remains in the list but has no marker.

### route

Used for route cards. It carries provider, mode, distance_m, duration_s, origin, destination, polyline, and hint.

Important details:

- Coordinates shown on AMap use gcj02.
- If origin comes from browser geolocation, the backend may return wgs84; the frontend converts it approximately to gcj02 before rendering.
- If polyline is empty, the frontend creates a fallback line from origin to destination.

### client_location

Used as the origin when building an AMap navigation URI. It represents browser geolocation in WGS84. The frontend converts it before using it on the map or in the URI. Typical fields include lng, lat, accuracy_m, city, and region_text.

### destination

Used to show the route card's destination name and address and to choose the preferred destination coordinate. If destination.geo.gcj02 exists, the frontend uses it for AMap navigation; otherwise it falls back to route.destination.

### view_payload

view_payload is a lightweight display instruction, not arbitrary HTML. Suggested fields:

```json
{
  "version": 1,
  "scene": "agent_route",
  "title": "Route from your location to Arcade One"
}
```

Supported scene values are agent_candidates and agent_route. If view_payload.scene is missing, the frontend infers agent_route when route exists, and otherwise agent_candidates when shops exist.

## Frontend rendering flow

### 1. App.tsx

Responsibilities:

- Extract ChatMapArtifacts from session details.
- Create pending route artifacts early from the SSE navigation.route_ready event.
- Pass activeMapArtifacts to ChatPanel.

Key state:

```ts
const [activeMapArtifacts, setActiveMapArtifacts] = useState<ChatMapArtifacts | null>(null);
```

### 2. ChatPanel.tsx

It renders user and assistant Markdown messages normally. When mapArtifacts is present, it appends AgentMapCard below the assistant response. The map card may appear while the response is still streaming. It enhances the Markdown body rather than replacing it.

### 3. AgentMapCard.tsx

It selects agent_candidates or agent_route, normalizes route coordinates, builds the map center, title, subtitle, and AMap actions, then delegates to lower-level components.

Candidate arcade scene:

```text
AgentMapCard
  -> AmapMapCanvas
  -> AmapShopMarkers
  -> MapActionBar
```

Route scene:

```text
AgentMapCard
  -> AmapMapCanvas
  -> AmapRouteOverlay
  -> MapActionBar
```

### 4. Map primitives

- AmapMapCanvas loads the AMap JS API, creates and destroys the map instance, and exposes AmapRuntime.
- AmapShopMarkers draws markers from shops[*].geo.gcj02, supports selection, and updates the selected arcade when a marker is clicked.
- AmapRouteOverlay draws route.polyline and the route origin/destination; coordinates are normalized first if they are not GCJ02.
- MapActionBar renders “Open in browser” and “Open AMap app” actions.

## Recommended Markdown usage

Do not ask the model to emit <AgentMapCard ... /> in Markdown. Arbitrary HTML would bypass React types, coordinate conversion, and URI construction.

Keep the Markdown readable, for example:

```markdown
I found a few candidate arcades for you. The map card is below.
```

Render the map from structured artifacts attached to the same assistant turn.

If Markdown-based map declarations are needed later, use an allowlisted code fence such as:

````markdown
```arcadegent-map
{
  "version": 1,
  "scene": "agent_route",
  "title": "Route from your location to Arcade One"
}
```
````

The parser should recognize only the arcadegent-map fence, accept JSON only, use the JSON only as an addition to view_payload or ChatMapArtifacts, and still render through AgentMapCard. It must reject HTML, JavaScript, style, and arbitrary component names. This keeps Markdown readable without making map rendering an uncontrolled model output.

## Debugging checklist

If the map card is missing, check:

1. Does ChatSessionDetail contain shops, route, destination, or view_payload?
2. Is activeMapArtifacts non-empty in App.tsx?
3. Did ChatPanel receive mapArtifacts?
4. Did AgentMapCard infer the correct scene?
5. Is VITE_AMAP_WEB_KEY configured, or does the test install window.__ARCADEGENT_AMAP_MOCK__?
6. Does each candidate marker have shop.geo.gcj02?
7. Does the route have route.destination or destination.geo.gcj02?
