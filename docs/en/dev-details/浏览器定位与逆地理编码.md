# Browser Geolocation and Reverse Geocoding

[简体中文](../../dev-details/浏览器定位与逆地理编码.md) · English · [日本語](../../ja/dev-details/浏览器定位与逆地理编码.md)

Last updated: 2026-03-20

## Background

To let the agent use the user's otherwise implicit current location when a session starts, the frontend obtains browser coordinates before sending the first message in a new session. If the cached location cannot be reused, the backend calls AMap's REST reverse-geocoding API to resolve the region and injects it into the agent context.

Design goals:

- Keep the AMap API key on the backend; never expose it to the browser.
- Separate browser geolocation from region resolution: the frontend obtains coordinates and the backend reverse-geocodes them.
- Put coordinates and region information directly in the agent's instructions instead of requiring it to infer them from a tool result.
- Let the conversation continue if geolocation fails or AMap is unavailable; only region details are omitted.

## End-to-end flow

```text
Page opens
  -> frontend warms up geolocation in the background and stores a local cache

First message in a new session
  -> frontend requests the latest browser coordinates
  -> if equivalent to the cached location, reuse its region details
  -> otherwise POST /api/location/reverse-geocode
  -> backend calls AMap /v3/geocode/regeo
  -> return province/city/district/township/formatted_address
  -> frontend adds location to POST /api/chat/sessions
  -> backend stores client_location in session memory
  -> ContextBuilder explicitly adds it to the instructions
```

## Frontend flow

Related files:

- apps/web/src/lib/clientLocation.ts
- apps/web/src/api/client.ts
- apps/web/src/App.tsx

### 0. Browser geolocation prerequisites

On public domains, navigator.geolocation works only in a secure HTTPS context. localhost and 127.0.0.1 are development exceptions. If a production page is opened over HTTP, the browser normally will not show the location permission prompt; the frontend treats this as a geolocation failure and does not add location to the session request.

For deployment, check that the site uses HTTPS and redirects port 80 to 443; that an outer Nginx, CDN, or iframe container does not disable geolocation with Permissions-Policy; and that the browser does not retain a previous denial for the site.

### 1. Warm the cache when the page opens

During initialization, App.tsx calls warmupClientLocationCache() to start a background location lookup.

Key functions in clientLocation.ts:

- getCurrentBrowserCoordinates(maximumAge) calls navigator.geolocation.getCurrentPosition.
- readLocationCache() and writeLocationCache() read and write localStorage.
- areEquivalentLocations() uses haversine distance to compare coordinates.
- warmupClientLocationCache() warms the cache when the page opens.
- resolveClientLocationForSessionStart() obtains a fresh location before sending a new session's first message.

Locations within 30 meters are considered equivalent. This avoids repeated reverse geocoding caused by small browser-position fluctuations.

### 2. Decide whether to reverse-geocode before starting a session

resolveLocation() follows this sequence:

1. Read the cached location.
2. Request the browser's current coordinates again.
3. If the cached and current locations are equivalent and the cache has region details, reuse it.
4. Otherwise call reverseGeocodeLocation(coords).
5. Write the new coordinates and region details back to the cache.

### 3. Backend endpoint called by the frontend

Endpoint:

```text
POST /api/location/reverse-geocode
```

Request:

```json
{
  "lng": 121.4737,
  "lat": 31.2304,
  "accuracy_m": 35
}
```

Response:

```json
{
  "lng": 121.4737,
  "lat": 31.2304,
  "accuracy_m": 35,
  "province": "上海市",
  "city": "上海市",
  "district": "黄浦区",
  "township": "外滩街道",
  "adcode": "310101",
  "formatted_address": "上海市黄浦区外滩街道...",
  "region_text": "上海市黄浦区外滩街道...",
  "resolved": true
}
```

## Backend flow

Related files:

- backend/app/protocol/messages.py
- backend/app/api/http/location.py
- backend/app/services/amap_reverse_geocoder.py
- backend/app/core/container.py

### 1. DTOs

messages.py defines ClientLocationContext, ReverseGeocodeRequest, and ReverseGeocodeResponse. ChatRequest.location is a ClientLocationContext, allowing the backend to pass the frontend's reverse-geocoding result into the agent runtime.

### 2. FastAPI endpoint

location.py exposes POST /api/location/reverse-geocode. It validates the request body and calls container.reverse_geocoder.reverse_geocode(request).

### 3. Container wiring

At startup, container.py creates AMapReverseGeocoder using the existing AMap REST settings:

- AMAP_API_KEY
- AMAP_BASE_URL
- AMAP_TIMEOUT_SECONDS

Route-planning REST fallback and reverse geocoding therefore share the same AMap configuration.

### 4. Call the AMap REST API

AMapReverseGeocoder.reverse_geocode() sends:

```text
GET {AMAP_BASE_URL}/v3/geocode/regeo
  ?key=...
  &location={lng},{lat}
  &extensions=base
  &roadlevel=0
```

The implementation currently uses Python's standard urllib.request.urlopen().

### 5. Parse the AMap response

The service extracts province, city, district, township, adcode, and formatted_address, assembles region_text, and returns the result to the frontend.

Special cases:

- For municipalities, AMap may return an empty city array; the service then uses province as city.
- If AMAP_API_KEY is unset, the network request fails, or the response format is invalid, the service returns resolved=false.

## Inject location into the agent context

Related files:

- backend/app/agent/runtime/react_runtime.py
- backend/app/agent/context/context_builder.py

### 1. Store it in session memory

After receiving ChatRequest, ReactRuntime stores request.location at state.working_memory["client_location"]. Later turns can reuse it even if they do not upload location again.

### 2. Add it to the instructions

ContextBuilder prefers the current request's location and otherwise falls back to working_memory["client_location"]. It injects the location in two places:

- runtime_hint.client_location
- Explicit instruction text headed “Client location context:”

The agent can then directly see WGS84 longitude/latitude, browser accuracy radius, province/city/district/township, and formatted address. This helps it interpret implicit context such as “nearby,” “current city,” “route origin,” and regional preferences.

## Fallback behavior

- Public page without HTTPS: the browser does not prompt for location and the frontend does not add location.
- User denies browser permission: the frontend falls back to cache; with no cache, it omits location.
- AMap reverse geocoding fails: coordinates are retained, but message sending continues.
- Backend has no AMAP_API_KEY: resolved=false, and chat continues.
