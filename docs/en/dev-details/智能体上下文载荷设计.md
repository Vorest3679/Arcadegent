# Agent Context Payload Design

[简体中文](../../dev-details/智能体上下文载荷设计.md) · English · [日本語](../../ja/dev-details/智能体上下文载荷设计.md)

## Purpose

This document records long-term engineering constraints for Arcadegent's agent orchestration, tool design, and context organization. It describes principles for future iterations rather than a one-time patch.

## Design Principles

### 1. Follow the Unix philosophy

Keep modules focused: each program should do one distinct job.

- A tool performs deterministic work such as execution, lookup, calculation, and formatting.
- An agent reasons and generates responses from context, skills, and tool observations.
- ContextBuilder organizes context for the model; it does not produce template-based answers on the model's behalf.
- A skill teaches the model how to read structured results; it does not hard-code response templates in application code.

Consequences:

- Do not call an LLM from inside a tool to create an “AI inside AI” flow.
- Do not make one module responsible for execution, reasoning, and presentation at the same time.
- When data becomes too large or semantically complex, split it into a directory and detail blocks instead of adding more fields to one payload.

### 2. Build an LLM-served agent, not a template agent

Use an LLM to serve the agent rather than reducing the agent to a template assembler.

- The agent should generate the final answer from structured context. A template-based summarizer such as summary_tool should not be the fallback for the main answer path.
- Templates may be used for deterministic formatting, but not as the primary reasoning path.
- Prompts and skills should teach the model how to read data and organize an answer, rather than predefining every response shape.
- If the model misses important details, improve the context structure instead of adding more template branches.

## Current Implementation

### 1. Summary generation moved from a tool back to the agent

- summary_tool remains as a deterministic formatter for compatibility.
- summary_agent handles the primary answer path.
- search_agent and navigation_agent no longer depend on summary_tool to produce the final user response.

This keeps tools as tools, avoids a hidden second LLM entry point, and lets the agent, skills, and context determine answer quality instead of a fixed template.

### 2. Context uses a “directory plus details” structure

context_payload is layered instead of flattening every field into one memory_snapshot. Its main blocks are:

- directory
- query
- search_catalog
- shop_details
- route

directory tells the model which blocks are available, what to read first, and what the current answer should focus on. search_catalog contains lightweight index information such as total, top_shops, and detail_sections. shop_details contains larger fields for specific shops, such as transport, arcades, and comment. route describes navigation separately from search results.

This structure helps the model identify the main point before exploring details, prevents large shop fields from competing with summary information for attention, and lets skills describe a stable reading order instead of patching over mixed JSON.

### 3. A skill is a guide, not a template library

Skills in skills/*/SKILL.md tell the model to read directory first, use search_catalog and route as primary answer anchors, treat shop_details as supporting detail, and distinguish supporting details from primary answer anchors.

The goal is not to prescribe fixed wording, but to make the model more reliable when reading structured context.

directory.skills contains only the names and descriptions of skills available to the current agent. The model loads the body and references on demand with read_skill; loaded content remains in context for the current turn, while tool history stores only the read receipt. See the [Skill Configuration and Extension Guide](../guidings/技能配置与扩展指南.md) for configuration, refresh, and isolation rules.

## Constraints for Future Work

When adding a tool, subagent, or context block, ask:

1. Does this module do only one kind of work?
2. Should this capability belong to a tool, agent, context builder, or skill?
3. Is a new field index information or detailed information?
4. If a field is large, should it go in a detail block instead of the catalog?
5. Are we turning the agent into a template agent?
6. Are we introducing nested LLM calls inside a tool?

## Conclusion

Arcadegent aims to build agents with clear responsibility boundaries, structured context that serves the LLM, skills that guide how context is read, and tools that keep execution deterministic. This is the default engineering direction for future work on context, summaries, and subagents.
