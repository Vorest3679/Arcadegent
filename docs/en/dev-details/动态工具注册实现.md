# Dynamic Tool Registration: Implementation Notes

[简体中文](../../dev-details/动态工具注册实现.md) · English · [日本語](../../ja/dev-details/动态工具注册实现.md)

## Purpose

This document records the engineering approach behind the built-in dynamic tool registry refactor. It covers the original problems, why a one-time migration was chosen over a compatibility layer, the boundaries changed during migration, the reasoning behind each step, and what the current design deliberately does not solve.

Because the codebase was updated in one step, the implementation path is included for future commit reviews and plugin-related work.

## Assumptions behind the decision

The key assumption was that this was a one-time codebase refactor and did not need to keep the old manifest format compatible.

Keeping compatibility would likely have required the provider to support both tools.json and tools_manifest.json, schema_model and input_schema, and handler and executor, with runtime branches for both formats. That would turn a cleanup into a permanent transition layer: more code and mental overhead, two formats to document, and legacy constraints on future tool package installation and removal.

Since a one-time update was allowed, the chosen approach was to remove the old entry point, switch directly to the new model, and give the provider, schema, and executor clear responsibilities. This is why no compatibility branch for the old tools.json was retained.

## Problems in the previous design

The built-in tools had a manifest, but the system was only partly dynamic.

### 1. The manifest externalized an index, not the tool itself

The old manifest named a tool, pointed to a Pydantic schema_model, and named a centralized handler. It was a reference table; it did not contain the schema or make the implementation local to the tool.

### 2. Schemas still required central Python registration

Adding a tool meant adding a Pydantic model under app.agent.tools.schemas and registering it in a central mapping. The schema did not travel with the tool.

### 3. Execution still required a central handler

Adding a tool also meant adding execute_xxx to handlers.py and referencing it from the manifest. The manifest looked dynamic while the actual business entry points accumulated in one Python module. That is not plug-and-play; it merely moves hard-coded registration into a handler file.

### 4. One tool touched several central locations

The old path usually required changes to the central schema file, central handler file, manifest, and tests. That did not meet the goal of a locally self-describing tool.

## Refactor goals

The goal was not simply to split JSON into smaller files. Built-in tools needed to become local units that the provider could assemble:

1. **Keep the schema with the tool.** Adding a tool should not require central registration in schemas.py.
2. **Keep execution with the tool.** Adding a tool should not require central registration in handlers.py.
3. **Make the provider an assembler, not a business hub.** BuiltinToolProvider should load the manifest and definitions, construct validators, and call executors without knowing tool-specific details.

## Before and after

### Previous structure

```text
tools.json
  -> schema_model: app.agent.tools.schemas:SomeArgs
  -> handler: app.agent.tools.builtin.handlers:execute_some_tool

app.agent.tools.schemas
  -> Pydantic models
  -> central schema registration

app.agent.tools.builtin.handlers
  -> execute_db_query
  -> execute_geo_resolve
  -> execute_route_plan
  -> execute_summary
  -> ...
```

The schema and handler were centrally registered despite being described as dynamic.

### Current structure

```text
backend/app/agent/tools/builtin/
  provider.py
  tools_manifest.json
  executor_utils.py
  executors/
    db_query.py
    geo_resolve.py
    route_plan.py
    summary.py
    select_next_subagent.py
  schemas/
    db_query_tool.json
    geo_resolve_tool.json
    route_plan_tool.json
    summary_tool.json
    select_next_subagent.json
```

tools_manifest.json is the index; schemas/*.json contain the tool definitions; executors/*.py provide each tool's entry point; executor_utils.py contains only small shared helpers.

## Migration steps and reasoning

### 1. Find the actual point of central coupling

The first step was to identify where the system remained centralized, rather than immediately editing JSON. ToolRegistry was already largely provider-based. The remaining coupling was in the built-in provider's references to central schemas and handlers. The refactor therefore focused on decentralizing the built-in provider's inputs and execution chain, not on further changing ToolRegistry.

### 2. Drop old-manifest compatibility

BuiltinToolProvider stopped supporting both tools.json and the new structure. This kept one provider model, one documented format, tests focused on the final format, and avoided legacy constraints on future bundle/plugin work.

### 3. Separate the top-level manifest from individual definitions

tools_manifest.json now has two jobs: declare shared services and list tool JSON files. It no longer embeds each full schema. Each schemas/*.json definition contains name, kind, description, executor, input_schema, capabilities, and metadata. Tool description and entry point can now be understood locally.

### 4. Make schemas self-describing JSON Schema

The issue was not that Pydantic was unsuitable; it was that a schema defined in a central Python module prevented local self-description. Each schemas/*.json now contains input_schema, which the provider reads and exposes through ToolDescriptor.

Runtime support required a generic JSON Schema layer that reads the JSON, applies defaults, resolves $ref recursively, handles anyOf and oneOf, and performs final validation with jsonschema. This logic lives in [backend/app/agent/tools/schemas.py](../../../backend/app/agent/tools/schemas.py). That module is now provider-neutral JSON Schema support, not a central collection of built-in argument models.

### 5. Replace the central handler with per-tool executors

Execution moved from one handlers.py into executors/db_query.py, geo_resolve.py, route_plan.py, summary.py, and select_next_subagent.py. Each definition binds its own import path, such as app.agent.tools.builtin.executors.db_query:execute. The provider no longer dispatches by tool name, new tools do not require execute_xxx in a central file, and each executor's changes stay local.

### 6. Keep shared helpers narrowly scoped

The refactor retained [executor_utils.py](../../../backend/app/agent/tools/builtin/executor_utils.py) for cross-tool pure helpers such as text truncation and region-code/name normalization. It must not become a renamed handlers.py or another central business module.

### 7. Redefine the provider boundary

[provider.py](../../../backend/app/agent/tools/builtin/provider.py) now loads tools_manifest.json, resolves shared services, reads each schemas/*.json, constructs ToolDescriptor and validators, and invokes executors. It does not know tool-specific Pydantic models or centralized handler names and does not branch on tool names for business behavior. It is an assembler.

### 8. Add a provider-neutral validation error

Built-in validation no longer depends on Pydantic, so the runtime needed a provider-neutral error. ToolInputValidationError was added to app.agent.tools.base, and ToolRegistry.execute() catches it and normalizes it to validation_error.

### 9. Update documentation and tests

The manifest guide was updated at [docs/guidings/内建工具清单编写指南.md](../guidings/内建工具清单编写指南.md). Issue tracking remains in the local archive rather than the public documentation. Provider and registry tests were updated in test_builtin_tool_provider.py and test_tool_registry.py. This closed the change across implementation, docs, and issue tracking.

## Important file mappings

### Old entry points to new entry points

- Old backend/app/agent/tools/builtin/tools.json -> new backend/app/agent/tools/builtin/tools_manifest.json.
- Old schema_model = app.agent.tools.schemas:SomeArgs -> input_schema defined as JSON Schema in schemas/*.json.
- Old handler = app.agent.tools.builtin.handlers:execute_xxx -> executor = app.agent.tools.builtin.executors.xxx:execute.

### Central files to local files

- app/agent/tools/schemas.py changed from central built-in argument models to generic JSON Schema helpers.
- backend/app/agent/tools/builtin/handlers.py was removed. Its logic moved to executors/*.py, and shared pure functions moved to executor_utils.py.

## Runtime flow

```text
tools_manifest.json
  -> provider reads services and tool paths
  -> provider reads schemas/*.json
  -> provider builds ToolDescriptor + validator + executor
  -> ToolRegistry collects definitions
  -> model requests a tool call
  -> ToolRegistry checks permissions and arguments
  -> BuiltinToolProvider invokes the matching executor
  -> executor obtains services through BuiltinToolContext
  -> executor returns a structured result
```

There is no central schema registry or central handler dispatcher in this flow.

## Benefits of the current structure

The minimum steps to add a built-in tool are now:

1. Add a tool JSON under schemas/.
2. Add its executor under executors/.
3. Add the JSON path to tools in tools_manifest.json.
4. Add shared services only if needed.

You no longer need to add a Pydantic model to central schemas.py, register execute_xxx in handlers.py, or add built-in fields or branches to ToolRegistry. The gain is fewer central registration points, not fewer files.

## Deliberately out of scope

The refactor makes built-in tools locally self-describing, but it does not create a complete plugin package manager. It deliberately does not add directory scanning for tool bundles, one-step ZIP parsing/loading, bundle install/uninstall commands, bundle version constraints or signatures, or hot-plug lifecycle management.

Those are separate plugin-management problems, expand the scope and risk, and were not needed to straighten the built-in provider boundary.

## Possible next steps

Two natural extensions are:

1. **Load a tool bundle from a ZIP.** Package schemas/*.json, executors/*.py, and tools_manifest.json as a distributable unit for the provider to unpack, validate, and assemble.
2. **Uninstall tools as a unit.** Remove an installed bundle and update registry refresh, local installation state, and health status together.

These should be treated as new plugin-management work, not unfinished parts of this refactor.

## Conclusion

The refactor is complete when all three statements hold:

1. Schemas no longer require central Python registration.
2. Execution logic no longer requires central handler registration.
3. The provider assembles tools without making tool-specific business decisions.

The result is a responsibility redesign, not just a file split. Built-in tools are closer to a pluggable provider instead of a mostly static system wearing a manifest.
