# 插件装配实现

本说明对应二级计划 5 的阶段 2c：agent 通用层新增插件协议与启动时静态安装，机厅业务通过 `ArcadePlugin` 注入钩子与工具。阶段 2d 才迁移技能、MCP 资源、agent 定义和提示词。

## 组成

| 位置 | 职责 |
| --- | --- |
| `backend/app/agent/plugins/spec.py` | `Plugin`、`PluginInfo`、`PluginConfig`（配置模型基类）、`PluginError` |
| `backend/app/agent/plugins/host.py` | 装配入口 `load_plugins(path, plugins=, environ=, trusted=, required=)`；`install_configured`、`install_plugins` 是它的后两步 |
| `backend/app/agent/plugins/composite.py` | `CompositeTurnDomain`：把多个插件的 `BaseTurnDomain` 合成内核唯一的 domain |
| `backend/app/agent/plugins/core.py` | `CorePlugin`：通用工具的 manifest 适配器（需按受信任安装） |
| `backend/app/agent/plugins/config.py` | 读取插件文件、展开占位符、按模型校验、检查密钥写法；`RelPath`、`secret_values` |
| `backend/app/core/container.py` | 创建插件实例，决定必需插件与受信任插件，调用 `load_plugins` |
| `backend/app/core/arcade_wiring.py` | 机厅宿主服务（逆地理编码、地理缓存、payload mapper），由 `Settings` 构建 |
| `backend/app/domain/arcade/plugin.py` | 机厅插件：hooks、业务工具、高德配置模型 |
| `backend/plugins.yaml` | 宿主维护的启用列表与配置值 |

依赖方向仍是 `domain`/`agent_host`/`core` → `agent`。插件文件的读取、展开、校验和安装都在 `app/agent/plugins/` 里，独立成包时可整体带走；该目录只 import `app.agent.*`、pydantic 和 PyYAML，边界测试会扫描它。

## 职责划分

- **agent 包**：从读插件文件到安装一步完成（`load_plugins`），对宿主只要求三样输入：插件实例、环境变量映射、宿主决定的信任与必需集合。agent 包不读进程环境，也不知道 `Settings`。
- **插件代码**：声明 `info`、`config_model`，通过 `__init__` 接收依赖，`hooks(config)`、`tools(config)` 只构造并返回对象。插件不按字符串查找服务，也不读环境变量。
- **宿主（container）**：用实际依赖创建插件实例，决定哪些必需（`REQUIRED_PLUGINS`）、哪些受信任（`TRUSTED_PLUGINS`），把 `settings.agent_plugins_file` 和 `os.environ` 交给 `load_plugins`。`Settings.from_env()` 已先把项目 `.env` 写入进程环境。测试与评测改传 `plugin_configs`，走 `install_configured`，不读生产配置。
- **`plugins.yaml`**：只选择启用哪些已知插件、按什么顺序安装，并提供配置值；不能指定代码，也不能声明信任。`main.py` 不参与插件装配。

## 安装流程

1. `read_plugins_file` 解析 YAML，拒绝重复键和非字符串键。
2. `resolve_plugin_configs` 校验外层结构与条目键，拒绝宿主未提供的插件名，跳过 `disabled: true` 的条目，展开占位符，再用插件的配置模型校验（相对路径以 YAML 所在目录为基准）。
3. 校验完成后检查密钥：遍历配置实例里所有 `SecretStr`（包括列表和字典中的），凡是 YAML 里写了值、但写法不是完整 `${VAR}` 或 `${VAR:-}` 的，一律报错。
4. `install_configured` 检查必需插件是否都已启用，再按宿主的信任集合为每个插件生成 `PluginEntry(plugin, config, trusted)`。
5. `install_plugins` 依次调用各插件的构建方法，校验返回类型、工具来源以及非受信任插件的保留能力；再做跨插件检查（插件名、工具名、独占 presenter）。全部通过后锁定各插件 provider 的运行时写入，并返回 `PluginSet`。
6. 失败时抛出 `PluginError`（配置问题是其子类 `PluginConfigError`），消息为 `plugin:<name>:<code>[:detail]` 或 `plugin_config:<code>`。安装是纯函数，失败前不会注册或锁定任何东西，所以不存在"半装"状态。阶段 5 的重载也按同样方式构建新一代 `PluginSet`，再替换引用。

`PluginSet.tool_providers` 是按插件名索引的映射，container 直接把它交给 `ToolRegistry`。

## 合成 domain

- 生命周期 `on_*` 按安装顺序调用。某个插件的钩子抛错时，后续插件的钩子照常执行，结束后再抛出第一个异常，异常 note 带 `plugin=<name> hook=<name>`。`CancelledError` 等非 `Exception` 异常立即抛出。外层 `LifecycleDispatcher` 仍负责保护 kernel memory、限制 `StateView` 写入，以及 `emit`/`emit_safe` 的语义。
- `runtime_hints`、`session_event_fields`、`tool_result_signal.completed_fields`、`worker_memory_promotions` 合并为一个字典，键冲突时报错并列出相关插件名。
- `tool_result_signal.events`、`artifacts_from_result` 按安装顺序拼接；`turn_summary` 拼接所有非空文本。
- `build_response`、`fallback_reply`、`turn_display_snapshot`、`build_worker_envelope` 不能合并，最多一个插件覆盖，冲突在构造组合 domain 时报错。
- 会话详情服务通过 `replies.ArcadeSessionDisplay(artifact_sink=...)` 取得展示投影，不依赖已安装的 turn domain。

## 工具与 provider 名

- provider 本身没有名字。`ToolRegistry(providers={name: provider}, local_provider=...)` 中映射的键是唯一的 provider 名，`/health`、`list_tools(provider=)`、`refresh_tools(provider=)` 都使用它。`ToolDescriptor` 不再包含 `provider` 字段。
- 每个插件拥有一个 `LocalToolProvider`，以插件名为键注册（`core`、`arcade`）。`local_provider` 如果不在映射里，会以 `runtime` 为键加入聚合。
- `LocalToolProvider` 只有两种来源：`plugin`（通过 `load`）和 `registered`（通过 `add`）。安装成功时对插件 provider 调用 `lock_runtime_writes(trusted=...)`，之后 `add`/`update`/`remove` 报 `runtime_writes_locked`；`load`（manifest 重载）仍可用，但非受信任插件不能借此加入保留能力。
- 这里刻意不用 `seal`：session 的 `RunLog.seal` 表示 run 结束、不再接收任何事件（终态，订阅者随后退出）；而 provider 的锁只关闭运行时增删改，`load` 和工具执行照常进行，provider 在整个进程生命周期内都在使用，语义不同。
- `CorePlugin` 用 manifest 适配器加载 `list_skills`、`read_skill`、`invoke_worker`；其中 `invoke_worker` 声明了 `spawn_agent`，所以 container 按受信任安装它。

## 配置与密钥

- YAML 格式：`plugins: {<name>: {disabled: bool, config: {...}} | null}`。外层只允许 `plugins`，条目只允许 `disabled`、`config`。插件配置模型继承 `PluginConfig`（`extra="forbid"`、`frozen=True`），未知字段由 pydantic 拒绝。
- 占位符只支持三种写法：`${VAR}`（变量缺失时报错）、`${VAR:-default}`、`${VAR:-}`。值整体为 `${VAR:-}` 且变量未设置或为空时，删除这个键，让模型默认值生效。环境变量的值本身含 `${` 时不会被误判为占位符写错。
- 密钥只能写成 `${VAR}` 或 `${VAR:-}`；带字面默认值或与其他文本拼接都会报错，错误信息只包含插件名、字段路径和错误类型。
- `RelPath` 以 `plugins.yaml` 所在目录为基准，空字符串报错。`AGENT_PLUGINS_FILE` 由 `Settings` 解析，规则与其他 agent 配置文件一致：先按当前目录找，找不到再按仓库根目录找。
- 高德配置：逆地理编码和地理缓存读取 `Settings.amap_*`（宿主服务）；路线工具读取 `plugins.yaml` 中 `arcade.config.amap`，其占位符引用同一组环境变量（计划第 4.2 节"宿主级/插件级"分工）。

## 健康检查

`/health` 的 `plugins` 列表中，每个插件给出 `name`、`version`、`trusted`、贡献清单（`hooks`、`tools`），以及各密钥字段的状态（只有 `set` / `missing`）。`tool_providers` 按注册表的键依次为 `mcp`、`core`、`arcade`、`runtime`。

## 当前边界

- 阶段 2c 的插件协议只有 `hooks` 和 `tools`。skill/MCP 资源、上下文分区、agent 定义和插件依赖（`requires`）留到对应阶段实现时，再与各自的适配器一起加入，现在不预留未实现的声明。
- 只支持启动时静态安装。卸载、重载和按 turn 绑定插件代际留到阶段 5。
