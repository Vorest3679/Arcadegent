# 插件装配实现

本说明对应二级计划 5 的阶段 2c 与 2d：agent 通用层提供插件协议和启动时静态安装，机厅业务通过 `ArcadePlugin` 注入钩子、工具、技能/MCP 资源与 agent 定义。阶段 2d 完成后，`app/agent/` 不再包含机厅提示词、技能、agent YAML、provider profile 或 MCP server 配置。

## 组成

| 位置 | 职责 |
| --- | --- |
| `backend/app/agent/plugins/spec.py` | `Plugin`、`PluginInfo`、`PluginConfig`、`PluginResources`、`PluginError` |
| `backend/app/agent/plugins/host.py` | 装配入口 `load_plugins`、`load_plugin_configs`、`install_configured`、`install_plugins`；agent 名册合并、别名校验与按插件解析 prompt |
| `backend/app/agent/plugins/resources.py` | 读取插件资源声明，构建技能根目录与 MCP server 配置 |
| `backend/app/agent/plugins/composite.py` | `CompositeTurnDomain`：把多个插件的 `BaseTurnDomain` 合成内核唯一的 domain |
| `backend/app/agent/plugins/core.py` | `CorePlugin`：通用工具 manifest 适配器与技能策略（需按受信任安装） |
| `backend/app/agent/plugins/config.py` | 读取插件文件、展开占位符、按模型校验、检查密钥写法；`RelPath`、`secret_values`、`config_placeholders` |
| `backend/app/agent/subagents/roster.py` | `AgentDefinition`、`AgentRoster` 及 YAML 覆盖 |
| `backend/app/agent/context/prompt_loader.py` | `FilePromptLoader`（安装时已解析的文件）与 `DirectoryPromptLoader`（单目录宿主/测试）；找不到即报 `PromptError` |
| `backend/app/core/container.py` | 创建插件实例，决定必需/受信任插件，先解析资源再装配运行时 |
| `backend/app/core/arcade_wiring.py` | 机厅宿主服务（逆地理编码、地理缓存、payload mapper），由 `Settings` 构建 |
| `backend/app/domain/arcade/plugin.py` | 机厅插件：hooks、业务工具、资源路径、agent 定义、高德配置模型 |
| `backend/app/domain/arcade/profiles.py` | 机厅 agent 默认定义、YAML 别名与资源路径 |
| `backend/app/domain/arcade/resources/` | prompts、skills、agents、MCP server 配置 |
| `backend/plugins.yaml` | 宿主维护的启用列表与配置值 |

依赖方向仍是 `domain`/`agent_host`/`core` → `agent`。插件文件的读取、展开、校验和安装都在 `app/agent/plugins/` 里，独立成包时可整体带走；该目录只 import `app.agent.*`、pydantic 和 PyYAML，边界测试会扫描它。

## 职责划分

- **agent 包**：从读插件文件到安装一步完成，对宿主只要求插件实例、环境变量映射、宿主决定的信任与必需集合。agent 包不读进程环境，也不知道 `Settings`。
- **插件代码**：声明 `info`、`config_model`、`resources`；基类成员的参数类型是 `config: Any`，子类直接标注自己的配置类（`config: MyConfig`），无需 `assert`/`cast`，类型由宿主安装前的 `isinstance` 检查保证；通过 `__init__` 接收依赖；插件作者只需从 `app.agent.plugins` 导入；`hooks(config)`、`tools(config)`、`agents(config)` 和 `resolved_resources(config)` 只构造并返回对象。插件不按字符串查找服务，也不读环境变量。
- **宿主（container）**：构造插件依赖，决定哪些必需（`REQUIRED_PLUGINS`）、哪些受信任（`TRUSTED_PLUGINS`）。它先读取配置和资源声明，构造 `SkillRegistry` 与 `MCPToolGateway`，再创建插件实例并安装。
- **`plugins.yaml`**：只选择启用哪些已知插件、按什么顺序安装，并提供配置值；不能指定代码，也不能声明信任。`main.py` 不参与插件装配。

## 安装流程

1. `read_plugins_file` 解析 YAML，拒绝重复键和非字符串键。
2. `resolve_plugin_configs` 校验外层结构与条目键，拒绝宿主未提供的插件名，跳过 `disabled: true` 的条目，展开占位符，再用插件的配置模型校验（相对路径以 YAML 所在目录为基准）。
3. 校验完成后检查密钥：遍历配置实例里所有 `SecretStr`（包括列表和字典中的），凡是 YAML 里写了值、但写法不是完整 `${VAR}` 或 `${VAR:-}` 的，一律报错。
4. container 检查必需插件，然后调用 `resolve_plugin_resources` 收集 `PluginResources`。技能根目录按安装顺序合并；MCP 目录逐个读取 JSON，`${config.<path>}` 由所属插件校验后的配置展开；server 名在所有插件、所有目录间唯一，冲突报 `duplicate_mcp_server:<server>:plugins:<先占用者>,<当前插件>`。
5. 用 `core.config.skills` 和技能根目录构造 `SkillRegistry`，用 MCP server 配置构造 `MCPToolGateway`。
6. `install_configured` 按宿主的信任集合为每个插件生成 `PluginEntry`；`install_plugins` 依次调用构建成员，校验返回类型、工具来源、保留能力，在该插件自己的 `resources.prompts` 中解析每个 agent 的 prompt（缺失即失败），再做跨插件检查。
7. 全部通过后锁定各插件 provider 的运行时写入，返回不可变 `PluginSet`。失败时抛出 `PluginError`（配置问题是其子类 `PluginConfigError`），消息为 `plugin:<name>:<code>[:detail]` 或 `plugin_config:<code>`，不包含配置值或路径。安装是纯函数，不存在"半装"状态。
8. container 用 `PluginSet.agents` 构造 `SubAgentBuilder`，用 `PluginSet.prompt_loader()` 构造 `ContextBuilder`，把 `PluginSet.tool_providers` 交给 `ToolRegistry`。

## 资源与 agent 名册

- `PluginResources` 是类级声明，宿主可在构造服务前读取：`skills` 是技能根目录，`mcp_servers` 是 MCP server JSON 目录，`prompts` 是本插件 agent prompt 的查找目录。`ArcadePlugin.resolved_resources` 根据 `arcade.config.mcp_servers_dir` 覆盖默认目录。
- `AgentRoster`（agent 名册）只包含 `agents`、`base_prompt`、`aliases`，构造后不可变（`allowed_tools`/`workers` 为 tuple，`aliases` 为只读映射）。prompt 目录属于 `PluginResources`；原 `tool_policies.yaml` 的 `read_only`/`concurrency_safe` 从未被运行时读取，已删除，并发由 `ToolSpec.execution_mode` 决定。每个 agent 显式声明 `role`（唯一的 `entry` 与若干 `worker`）和 `workers`；内核的 `AgentNode.spawnable` 直接取 `workers`，不再推断"入口 agent 可调度其余全部"。
- `AgentRoster.from_yaml` 读取 `definitions_dir`：`status: planned` 跳过，`subagent_name` 或别名表定位已有 agent，`allowed_tools_mode` 支持 merge/replace，`prompt_file`/`model`/`reasoning_effort`/`workers` 可覆盖。目录不存在、YAML 无法解析或顶层不是映射都报错（`missing_agent_definitions_dir` / `invalid_agent_yaml`），`skill_files` 报 `unsupported_agent_yaml_key:skill_files`；这些 `AgentRosterError` 码会原样透传为 `plugin:<name>:<code>`。
- 多插件合并时：agent 名、入口 agent、base prompt 与别名冲突都会报错并列出插件名；worker 必须指向已安装的 `role="worker"` agent。合并按表单次扫描，每张表存 `键 -> (所属插件, 值)`，冲突时无需二次查找。
- 别名只用于旧会话/YAML id：别名不能与任何真实 agent 名相同（`alias_shadows_agent`），目标必须是本插件自己的 agent（`unknown_alias_target`）；`SubAgentBuilder.get` 先查真实名再查别名。这避免了未受信插件用别名把其他插件的 worker 名重定向到自己的 agent，从而绕过 `spawnable` 白名单。
- `core.config.skills` 使用 `SkillSettings` 模型（禁用项、agent 白名单、两个字节上限）；技能目录本身来自插件资源，不再有 `backend/skill.config.py`。
- prompt 只在所属插件的 `resources.prompts` 中按顺序查找，同名文件不会被其他插件覆盖；绝对路径与含 `..` 的名字不匹配。基础 prompt 同样在声明它的插件目录中解析；多个插件声明不同的基础 prompt 文件报 `base_prompt_conflict`。`ContextBuilder` 不再内置 `system_base.md` 默认值。
- 插件未提供任何 agent 时，`PluginSet.agents` 为空；container 仍要求机厅插件提供包含唯一入口 agent 的名册。

## 合成 domain

- 生命周期 `on_*` 按安装顺序调用。某个插件的钩子抛错时，后续插件的钩子照常执行，结束后再抛出第一个异常，异常 note 带 `plugin=<name> hook=<name>`。`CancelledError` 等非 `Exception` 异常立即抛出。外层 `LifecycleDispatcher` 仍负责保护 kernel memory、限制 `StateView` 写入，以及 `emit`/`emit_safe` 的语义。
- `runtime_hints`、`session_event_fields`、`tool_result_signal.completed_fields`、`worker_memory_promotions` 合并为一个字典，键冲突时报错并列出相关插件名。
- `tool_result_signal.events`、`artifacts_from_result` 按安装顺序拼接；`turn_summary` 拼接所有非空文本。
- `build_response`、`fallback_reply`、`turn_display_snapshot`、`build_worker_envelope` 不能合并，最多一个插件覆盖，冲突在构造组合 domain 时报错。
- 会话详情服务通过 `replies.ArcadeSessionDisplay(artifact_sink=...)` 取得展示投影，不依赖已安装的 turn domain。

## 工具与 provider 名

- provider 本身没有名字。`ToolRegistry(providers={name: provider}, local_provider=...)` 中映射的键是唯一的 provider 名，`/health`、`list_tools(provider=)`、`refresh_tools(provider=)` 都使用它。
- 每个插件拥有一个 `LocalToolProvider`，以插件名为键注册（`core`、`arcade`）。`local_provider` 如果不在映射里，会以 `runtime` 为键加入聚合。
- `LocalToolProvider` 只有两种来源：`plugin`（通过 `load`）和 `registered`（通过 `add`）。安装成功时对插件 provider 调用 `lock_runtime_writes(trusted=...)`，之后 `add`/`update`/`remove` 报 `runtime_writes_locked`；`load`（manifest 重载）仍可用，但非受信任插件不能借此加入保留能力。
- `CorePlugin` 用 manifest 适配器加载 `list_skills`、`read_skill`、`invoke_worker`；其中 `invoke_worker` 声明了 `spawn_agent`，所以 container 按受信任安装它。

## 配置与密钥

- YAML 格式：`plugins: {<name>: {disabled: bool, config: {...}} | null}`。外层只允许 `plugins`，条目只允许 `disabled`、`config`。插件配置模型继承 `PluginConfig`（`extra="forbid"`、`frozen=True`），未知字段由 pydantic 拒绝。
- 占位符只支持三种写法：`${VAR}`（变量缺失时报错）、`${VAR:-default}`、`${VAR:-}`。值整体为 `${VAR:-}` 且变量未设置或为空时，删除这个键，让模型默认值生效。环境变量的值本身含 `${` 时不会被误判为占位符写错。
- 密钥只能写成 `${VAR}` 或 `${VAR:-}`；带字面默认值或与其他文本拼接都会报错，错误信息只包含插件名、字段路径和错误类型。
- `RelPath` 以 `plugins.yaml` 所在目录为基准，空字符串报错；Windows 盘符路径按绝对路径处理。`AGENT_PLUGINS_FILE` 由 `Settings` 解析，规则与其他 agent 配置文件一致。
- MCP server JSON 中的 `${config.<path>}` 只引用所属插件校验后的配置，不再读取进程环境；未知占位符按 `invalid_mcp_servers` 安装失败。日志与 `/health` 只显示脱敏后的 URL。
- 高德配置：逆地理编码和地理缓存读取 `Settings.amap_*`（宿主服务）；路线工具与高德 MCP server 读取 `plugins.yaml` 中 `arcade.config.amap`，其占位符引用同一组环境变量。
- `AGENT_NODES_DEFINITIONS_DIR`、`AGENT_SUBAGENT_YAML_OVERLAY_ENABLED`、`MCP_SERVERS_DIR` 仍可用，但由 `plugins.yaml` 的 `arcade.config` 接收；相对路径以 `backend/` 为基准。`AGENT_TOOL_POLICY_FILE` 与 `mcp_defaults.allow_all` 已删除。
- MCP 权限只看 agent 自己的 `allowed_tools`（精确名或 `mcp__*`），不存在跨插件的全局放行开关。
- **迁移**：自定义 `MCP_SERVERS_DIR` 中的 JSON 若仍写 `${AMAP_API_KEY}` 这类环境变量占位符，启动会以 `plugin:arcade:invalid_mcp_servers` 失败；改为 `${config.amap.api_key}`，并在 `plugins.yaml` 中把环境变量映射到对应配置字段。

## 健康检查

`/health` 的 `plugins` 列表中，每个插件给出 `name`、`version`、`trusted`、贡献清单（`hooks`、`tools`、`agents`），以及各密钥字段的状态（只有 `set` / `missing`）。`tool_providers` 按注册表的键依次为 `mcp`、`core`、`arcade`、`runtime`。

## 当前边界

- 上下文分区（`ContextSection`）仍由阶段 4 引入；当前 `ContextBuilder` 只改为从插件 prompt 目录加载提示词。
- 只支持启动时静态安装。卸载、重载和按 turn 绑定插件代际留到阶段 5。
- 插件 `requires` 依赖排序尚未实现；当前 `plugins.yaml` 的键顺序就是安装顺序。
