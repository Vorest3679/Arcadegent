# 会话加载性能优化

本文记录会话列表、切换会话和删除会话变慢的诊断过程与修复。两件事起了决定作用：**前端立即给出加载态**，以及**后端到数据库的 select 只取界面用得到的数据**。对应源码：`apps/web/src/hooks/useChatSessionController.ts`、`apps/web/src/components/chat/ChatPanel.tsx`、`backend/app/api/http/chat.py`、`backend/app/infra/db/online/session_repository.py`、`backend/app/services/chat_session_summary.py`、`supabase/migrations/`。

## 现象

- 点击历史会话后，面板要停顿数秒才有反应，期间仍显示上一个会话。
- 删除会话后整个侧边栏和面板一起卡住，直到请求全部返回。
- 会话列表首次加载也很慢。

## 诊断方法

先定位耗时发生在哪一段，再动代码：

1. **后端访问日志**：`app.access` 记录了每个请求的总耗时，先确认慢的是接口本身，而不是浏览器端渲染。
2. **分段计时**：在后端容器内对同一个请求拆成「数据库读取」「`_to_detail` 投影」两段计时，同时给 `httpx` 发出的外部请求逐个计时（包括失败的请求）。
3. **数据体积**：直接查询数据库，统计一行会话里各字段、`payload` 各子键的大小，找出被读取却从未展示的部分。
4. **前端交互计时**：首屏用 Lighthouse 测量；它只能覆盖首次加载，切换会话这类交互另用 Playwright 脚本记录「点击 → 出现加载态 → 内容出现」的时间，以及每个 API 请求的耗时与体积。

按日志总耗时的分布判断：如果耗时随网络波动、与会话内容大小相关，问题在数据传输；如果每次都差不多固定、并伴随外部请求，问题在同步调用外部服务。

## 根因

| 位置 | 问题 |
| --- | --- |
| 列表接口 | `select=*` 读取每个会话的整行，包括全部 `turns` 和 `working_memory`，只为算出标题、预览和消息数 |
| 详情接口 | 整行读取单个会话。一行里大部分是工具结果、worker 记录和 `worker_runs`，详情页从不展示；网络波动时耗时成倍增长 |
| 删除接口 | 删除前整行读取两次（接口层检查一次，仓库层归属检查再读一次） |
| 详情投影 | 对缺坐标的机厅同步调用地理编码；失败结果不缓存，每次读详情都重复付出外部请求的耗时 |
| 前端 | 切换会话时不清空旧内容、没有加载态；删除后重新拉取整个会话列表；流式输出时历史回合随每个 token 重渲染 |

## 方案一：前端加载态

目标：任何点击都在一帧内有可见反馈，不让用户对着旧内容等待。

- **切换会话**：点击后立即把该会话设为当前会话（侧边栏立刻高亮），清空面板并显示转圈 SVG（`role="status"`、`aria-label="加载会话中"`），详情返回后替换。加载中不显示空状态页，避免先闪一下「今天想查哪家机厅？」。
- **详情缓存**：控制器按会话保存最近一次加载的详情。再次切换到已加载过、且没有运行中 run 的会话时，先用缓存渲染，再在后台静默刷新（不显示加载态）。运行中的会话不用缓存，避免用过时快照接流。
- **删除会话**：删除当前会话时，确认后立即回到开始面板，不等请求返回；成功后只在本地从列表移除，不再重新拉取列表；失败时弹窗提示，不重新进入该会话。
- **渲染开销**：回合组件 `memo`，流式文本只传给正在运行的那一轮；流式气泡的 Markdown 解析使用 `useDeferredValue`；地图卡片 `memo`。

加载态只解决感知问题，接口本身仍需要变快，见方案二。

## 方案二：后端到数据库的 select 优化

原则：读取路径按界面需要投影，写入路径保持不变。运行时仍读写完整的 `chat_sessions` 行。

### 列表：摘要列

- `chat_sessions` 增加 `title`、`preview`、`visible_turn_count` 三列，由后端在每次保存会话时计算并写入（`ChatSessionMapper.to_record`）。
- 计算规则只在 `services/chat_session_summary.py` 维护一份：标题取第一条用户消息、预览取最后一条可见消息（折叠空白并截断）；可见消息只包括用户消息和对话层的最终回复，不包括模型中间文本、工具记录和 worker 文本。
- 列表接口改调用仓库的 `list_session_summaries`，只 select 摘要列，不传 `turns`。
- 存量数据由迁移用 SQL 按同一规则回填。回填期间停用 `updated_at` 触发器，否则所有会话的更新时间会被改写，列表顺序被打乱。`title` 为空的行（未回填）由仓库读取 `turns` 现算，保证结果正确。

### 详情：只读视图

- 新增视图 `chat_session_details`，行结构与表一致（不含详情接口用不到的 `title`、`preview`、`visible_turn_count` 摘要列），但：
  - `turns` 中工具记录和 worker 文本的 `content` 置空；`payload` 只保留 `status`、`map_artifacts`，以及模型调用是否带工具调用（布尔值）。
  - `working_memory` 去掉 `worker_runs`。
- 仓库新增 `get_session_for_display`，只用于详情接口。它返回的状态是不完整的，**不得写回存储，也不得交给运行时**；需要完整状态的路径（派发、取消、运行时）继续用 `get_session`。
- 视图的投影必须覆盖 `_to_detail` 读取的全部字段。修改 `_to_detail`、`_to_step` 或可见消息规则时，要同步检查视图，并重新做等价性验证（见下文）。

### 删除：只查归属字段

- 归属检查只 select `session_id, client_id` 两列。
- 接口层不再预先读取整行；只有会话正在运行、需要区分 404 与 409 时才读取一次，保证不暴露其他客户端的会话存在与否。

### 附：地理编码失败缓存

`ArcadeGeoResolver` 对失败的地理编码在进程内记录一段时间（`failure_ttl_seconds`，默认 600 秒），期间同一机厅不再重试。成功结果仍写入文件缓存。服务重启后第一次读到这些机厅时仍会付一次外部请求的耗时。

## 部署与迁移约束

- 先执行数据库迁移，再部署新后端。新后端保存会话时会写入摘要列，详情接口依赖视图；表结构不全时，写入会被数据库拒绝，详情接口会报错。
- Supabase CLI 以迁移文件名中第一个 `_` 之前的数字作为版本号。同一天的两个迁移如果都写成 `YYYYMMDD_00000N_*.sql`，版本号相同，推送会因主键冲突失败（迁移在事务中整体回滚）。新迁移要保证这段数字唯一且递增。
- 视图和摘要列都没有对 `anon`、`authenticated` 授权，与表一致，只通过后端的 service role 访问。

## 验证

- **等价性**：把会话数据导入临时本地 Postgres，执行全部迁移后，逐个会话比较「整行」与「视图行」经过 `_to_detail` 的输出，必须完全一致；同时比较 Python 摘要规则与 SQL 回填结果（标题截断、空白折叠、模型中间文本与 worker 文本不计入、`updated_at` 不变）。临时容器用完即删，数据不落盘到仓库。
- **单元测试**：仓库层覆盖摘要列读取不含 `turns`、存量行回退、保存时写入摘要列、详情走视图并保留客户端归属检查；地理编码覆盖失败缓存与过期重试。
- **端到端**：Playwright 覆盖点击会话立即高亮并显示加载态、删除当前会话立即回到开始面板、删除失败弹窗且不重新进入、删除后不重新拉取列表。
- **冷请求对比**：修改前（优化前的提交，用 git worktree 检出）与修改后在同一台机器、同一数据库上交替运行。每个样本都启动一个全新的后端进程：没有已建立的连接，失败缓存为空，地理编码文件缓存从同一份副本开始。只发 GET 请求。两个版本的响应体逐字节相同。

  | 场景（中位数，秒） | 修改前 | 修改后 |
  | --- | --- | --- |
  | 列表，进程内第一个请求（5 轮） | 3.09（2.77–4.14） | 0.55（0.47–0.87） |
  | 详情，进程内第一个请求（6 轮，3 个会话轮换） | 3.1（1.85–5.43） | 1.1（0.85–1.75） |
  | 详情，列表之后首次打开该会话（5 轮 × 3 个会话） | 0.56–3.95 | 0.35–1.01 |
  | 详情，含地理编码失败的会话（列表之后首次打开） | 3.36（3.26–3.95） | 0.94（0.67–1.01） |

  修改后的冷请求仍包含建立数据库连接与一次地理编码失败的耗时；同一进程内再次请求为 0.2–0.5 秒。详情读取的数据量约为原来的九分之一。
- **前端**：点击会话后加载态在 100 毫秒内出现；再次切换到已加载过的会话，内容约 0.3 秒出现（先展示缓存）。
- **首屏**：Lighthouse 桌面性能评分 100（FCP 0.5 秒，TBT 0 毫秒，CLS 0）。

## 仍存在的限制

- 详情接口的冷请求仍受数据库网络延迟影响；`map_artifacts` 中的机厅列表随会话增长，没有进一步裁剪。
- 地理编码失败缓存只在进程内，服务重启后会重新尝试一次。
- 前端详情缓存只在当前页面生命周期内有效，刷新页面后第一次打开仍需等待接口。
